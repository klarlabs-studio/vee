# Vee

See the [local historical review benchmark guide](docs/local-historical-review-benchmark.md) for reviewer-quality evaluation without a hosted service.

Run `vee analytics` for repository-local counts of saved reviews, each review's latest gate decision, finding lifecycle/severity, persisted verification outcomes by profile, recognized test failure/retry/flaky events in saved verification logs, explicit reviewed feedback labels, provider adapter latency, and token usage. Provider latency reports sample counts and nearest-rank p50/p95 wall-clock duration over the latest 500 reviews; it excludes cached outcomes, review preparation, and policy evaluation, and does not represent model compute time. Provider-reported token counts are aggregated when available (currently OpenAI-compatible API, Gemini CLI, Claude CLI, and Codex CLI JSONL responses). Optional user-maintained per-model token prices in `.vee.yaml` enable informational USD estimates; estimates require explicit input/output usage and a matching model rate, exclude cache-tier pricing and billing adjustments, and never affect review gates. Test event totals are observations from saved artifacts, not complete CI denominators or a flaky-test rate. JSON also reports observed finding-accuracy and actionability rates among uniquely labeled finding/snapshot pairs. Contradictory labels are excluded from each denominator and counted as disputed; these rates describe only reviewed occurrences and are not population estimates. Use `vee analytics --output json` for the versioned [quality-analytics-v9](schemas/quality-analytics-v9.schema.json) contract.

Configure prices using the exact model identifier recorded by the provider adapter; Vee does not fetch or update rates:

```yaml
providers:
  codex:
    kind: codex_cli
    executable: codex
    pricing:
      model-id-from-provider:
        input_usd_per_million: 2.5
        output_usd_per_million: 10
```

Record explicit feedback separately from lifecycle state with `vee findings feedback set FINDING_ID --snapshot SNAPSHOT_ID --label confirmed|false-positive|actionable|not-actionable --reason "..." --reviewer "..."`; retrieve it later with `vee findings feedback list [--finding FINDING_ID]`. The snapshot must be one where the finding occurred; repeating the exact same label is idempotent. Feedback labels are attributed records, not authenticated identities or gate inputs. MCP clients can use `record_finding_feedback`; analytics count the labels but do not infer precision/recall from them. JSON for each saved record follows [finding-feedback-v1.schema.json](schemas/finding-feedback-v1.schema.json).

Vee is a local-first tool for reviewing code changes and evaluating deterministic quality gates. It is independent of any orchestrator and exposes a CLI contract first.

## Status

Rust CLI, stdio MCP server, and optional local UI (loopback only; direct network access awaits native TLS support). `vee review` captures Git changes into a content-addressed snapshot, resolves merge-base for `--base`, invokes configured CLI or OpenAI-compatible API reviewers with bounded execution, evaluates a local deterministic policy, and persists review records in SQLite under `.vee/vee.sqlite`. The configured `review.include` and `review.exclude` globs limit changed-file context sent to reviewers; all captured changes remain in the snapshot used for stale-review checks. Each textual changed file includes its baseline and captured contents so reviewers can reason about the actual change. Binary, non-UTF-8, and LFS pointer content is disclosed as omitted and makes reviewer analysis incomplete. Provider output must match [provider-findings-v1.schema.json](schemas/provider-findings-v1.schema.json). Vee assigns finding identity and model-inference provenance; providers cannot submit those fields. Reviewers with malformed output, nonzero exit, or timeouts make the review incomplete.

The local UI's **Insights** view charts saved reviews using each review's latest gate decision and showing reviews without a gate separately. Provider latency compares measured adapter p50/p95 durations and daily history across the latest 2,000 reviews with measured, unmeasured, and failed sample counts; exports include the selected date/provider measurements and history coverage. These values exclude cached outcomes, preparation, and gate evaluation and do not represent model compute time. Choose the 7 or 14 latest active dates, or set a custom inclusive start/end date range. Save named filter and date-range views in the current browser profile for this local Vee instance. Gate trend date filters apply to the available latest 500 saved reviews; exports record the date bounds and completeness state. Finding severity shows current unique findings; feedback is shown only as explicit label counts. Export JSON or CSV from Insights to retain the displayed gate trend window alongside full severity/feedback counts and completeness notes. The dashboard never treats unlabeled findings as accepted/rejected feedback or presents those counts as a quality rate.

## Install

With Homebrew, on macOS or Linux:

```sh
brew install klarlabs-studio/tap/vee
```

Each release also attaches binaries for Linux (x86_64, arm64), macOS (arm64, x86_64) and Windows (x86_64), with a checksum and build provenance for each archive, and an installer for each platform. On Linux or macOS:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/klarlabs-studio/vee/releases/latest/download/vee-installer.sh | sh
```

On Windows (PowerShell):

```powershell
irm https://github.com/klarlabs-studio/vee/releases/latest/download/vee-installer.ps1 | iex
```

The installers put `vee` in `~/.local/bin` (set `VEE_INSTALL_DIR` to change it) and refuse an archive whose checksum does not match. To check where an archive was built, run `gh attestation verify <archive> --repo klarlabs-studio/vee`. The Linux binaries need glibc 2.35 or later; on musl systems such as Alpine, build from source or use the container image. For CI runners there is a container image, `ghcr.io/klarlabs-studio/vee`, built from the same release binaries. It runs as a non-root user and holds Vee and Git, which suits API providers; a reviewer that uses an agent CLI needs that CLI added in a derived image.

## Reviews on pull requests

`vee init --ci github --provider anthropic-api --model <model>` writes a GitHub workflow that uses the Vee action (`klarlabs-studio/vee`, [action.yml](action.yml)) to review every pull request on your runner with your model key and publishes a check and finding threads; `--ci gitlab` writes a pipeline file that includes the [GitLab template](integrations/gitlab/vee.gitlab-ci.yml) for merge requests. In CI, `vee ci run` detects the pull request, reviews it from its base, publishes the result, and exits with the gate (0 pass, 1 block, 2 incomplete). JSON output follows [schemas/ci-run-v1.schema.json](schemas/ci-run-v1.schema.json). On GitHub, people with write access can also comment `@vee review`, `status`, `explain`, `fix`, `dismiss` or `waive` on a pull request ([ADR 0020](docs/adr/0020-commands-in-pull-request-comments.md), [ADR 0023](docs/adr/0023-fixes-from-pull-request-comments.md)). See [the pull request guide](docs/guides/pull-requests.md) and [ADR 0019](docs/adr/0019-reviews-on-pull-requests-run-in-the-teams-ci.md).

## Reviews while you work

The Claude Code plugin reviews an agent's changes before the agent finishes its turn, and keeps the agent working on blocking findings (`VEE_AGENT_REVIEW=off` turns this off). `vee hooks install` adds an optional `pre-push` hook that stops a push the gate blocks. Both act only in repositories with a `.vee.yaml`. See [using Vee day to day](docs/guides/daily-use.md) and [ADR 0021](docs/adr/0021-reviews-at-hand-off-points.md).

## Build

Building the complete workspace requires Rust 1.89 or later (stable) and a Git executable. The checked-in `web/dist` bundle is embedded in the CLI at compile time; Node.js 22 and npm are needed only to rebuild the UI or run browser tests. Install Vee from a source checkout with:

```sh
cargo build --workspace --locked
cargo install --path crates/vee-cli --locked --root "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"
vee --version
cargo run -p vee -- init
cargo run -p vee -- review --base main --gate --output json
cargo run -p vee -- review --commit HEAD~1 --gate --output json
cargo run -p vee -- pr draft --base main --reviewer correctness
cargo run -p vee -- impact --commit HEAD~1 --output json
cargo run -p vee -- gate check --review rev_<id> --output json
```

Draft a pull request title and body from the captured change snapshot with `vee pr draft --base main --reviewer correctness`; `--staged`, `--working-tree`, and `--commit <oid>` select other scopes. The selected configured reviewer supplies the provider and instructions. Context is bounded by the repository review limits, and output is schema-validated, bound to the snapshot ID, and tagged with an output digest. JSON mode writes one versioned document to stdout and diagnostics to stderr. This command does not publish to a Git host, persist a review, or affect a gate. Its generated text is an unapproved draft; verify claims and tests before using it. See [schemas/pr-description-v1.schema.json](schemas/pr-description-v1.schema.json).

Generate an opt-in test patch proposal with `vee tests generate --base main --reviewer correctness` (or select `--staged`, `--working-tree`, or `--commit <oid>`). Vee supplies bounded snapshot and impact context to the configured reviewer, then checks the returned unified diff in an isolated temporary copy before saving it under `.vee/proposals/`. The versioned [test-patch-proposal-v2](schemas/test-patch-proposal-v2.schema.json) record binds the patch, source scope, and sandbox result to an exact proposal ID. Generation never changes the worktree or runs proposed tests. Inspect the saved diff, then apply a mutable-scope proposal with `vee tests apply <proposal-id> --approve <proposal-id>`; this explicit digest approval is required, and applying asks for confirmation at a terminal as `findings apply-patch` does. Commit-scope proposals are inspection-only because their source snapshot is immutable. Run only a repository-configured verification profile with `vee tests run <proposal-id> --profile <trusted-test-profile>`. Vee rejects stale source/target snapshots, records the post-application snapshot, and persists the verification result against that exact snapshot. If the trusted run fails, `vee tests refine <proposal-id> --run <failed-run-id>` supplies bounded parsed diagnostics and the prior test patch to the configured reviewer, then saves a new independently digest-bound proposal. The new patch still needs its own explicit approval and application before another run. The profile command is trusted repository configuration and runs with the same timeout/output limits as other verification profiles; Vee does not provide OS-level isolation.

Test generation ranks changed test/source pairs and impact-linked tests and source files, then applies `test_generation.max_context_tokens` (default 20,000; range 1,024–131,072) alongside the byte/file limits. Its token count is an estimate based on serialized context size, with reserved room for instructions and provider framing; it is not provider-reported usage. The proposal records a digest of the exact context, context roles, file digests, the estimate, and omitted paths. If the selected context exceeds the configured estimate, generation stops before invoking the provider.

To check whether that trusted profile detects a seeded behavior defect, first apply the test proposal and obtain a passing run on its exact post-application snapshot. Then pass a source-only mutant patch stored outside the repository: `vee tests effectiveness <proposal-id> --profile unit --mutant-patch /path/to/mutant.patch --output json`. Vee repeats the profile in a bounded temporary copy before and after applying the mutant, leaves the worktree unchanged, and writes a digest-addressed report conforming to [test-effectiveness-v4](schemas/test-effectiveness-v4.schema.json). When the passing baseline run emits LCOV, the report includes changed-line coverage for each mutated file, with the coverage run and exact snapshot recorded. The command digest binds the configured profile, resolved executable identity and bytes, and digests of present allowlisted environment values; raw values are never written to the report. Vee rejects a run if the executable or allowlisted environment changes during execution. Transitive tools, operating-system state, and external services are not fingerprinted. Outcomes are `killed`, `survived`, or `inconclusive`; this single-mutant diagnostic is not a calibrated test-quality score, and the temporary copy is not an OS security sandbox.

For repeatable aggregate evidence, create a versioned JSON corpus conforming to [test-mutant-corpus-v2](schemas/test-mutant-corpus-v2.schema.json), with one digest-pinned patch file per mutant, then run `vee tests effectiveness-corpus <proposal-id> --profile unit --manifest /path/to/corpus.json --output json`. Vee validates each patch digest and corpus path, assesses up to 50 mutants against the same approved snapshot and trusted profile, and persists a digest-addressed report conforming to [test-effectiveness-corpus-v6](schemas/test-effectiveness-corpus-v6.schema.json). The v2 manifest requires a dataset kind (`seeded` or `historical`) and source description, with optional source revision and license; the report binds this provenance into the corpus digest. Legacy v1 manifests remain supported and are labeled `unclassified` in v6 reports. Provenance is caller-supplied metadata and does not independently authenticate the source. Each mutant record binds the outcome to its exact mutated snapshot, modified production paths, and captured stdout/stderr digests; when the passing baseline run emits LCOV, each result also carries changed-line coverage for its mutated files, bound to the exact baseline snapshot and coverage run. Baseline-inconclusive cases are marked `not_run` and carry no mutated execution evidence. The report binds the configured test command digest to the saved baseline run. Kill signals use deterministic Go `-json`, nextest JSON, JUnit XML, Python `unittest` failure lines, Node.js test-runner failure markers, Minitest, Java enabled-assertion failures, and common text test-failure records; compiler/build errors alone are inconclusive, not killed. Seeded Rust, Python, Java, Go, JavaScript, TypeScript, and Ruby acceptance fixtures exercise killed and surviving mutants, including retry-boundary and path-traversal regressions. CI is configured to install the required runtimes and language services in its Linux, macOS, and Windows Rust jobs, but hosted Windows results have not yet been verified. These are reproducible fixture results, not representative historical effectiveness benchmarks. The report lists each outcome and keeps inconclusive mutants in the denominator; aggregate counts describe only the supplied corpus and are not a calibrated score. Its command digest also binds executable identity/content and present allowlisted environment-value digests, without recording raw values; transitive tools, operating-system state, and external services remain outside the fingerprint.

The CLI integration acceptance consumes a reusable, digest-pinned Rust example corpus at `crates/vee-cli/tests/fixtures/effectiveness/rust/`. It contains one return-value regression that the fixture test must kill and one comment-only change that should survive; the example is synthetic and only meaningful with the matching Rust fixture and trusted test profile.

To evaluate reviewer defect recall separately from test effectiveness, use `scripts/historical-review-benchmark.py` with already-cloned local repositories, full commit IDs, digest-pinned curator labels, and an explicit trusted Vee config. It reviews each defect-introducing commit in a disposable worktree, ignores repository-controlled Vee provider configuration, and writes per-case review JSON plus a recall report to the selected local output directory. Repeat `--verify-profile <id>` to run only explicitly selected profiles from that trusted config against the same commit snapshot; add `--verify-fix` to run those profiles against the case's pinned fix commit in a separate local worktree. Verification outcomes stay separate from AI recall. The [benchmark guide](docs/local-historical-review-benchmark.md) documents the manifest and label schemas. This harness has synthetic local fake-provider and verification-profile acceptance; Vee does not bundle a third-party historical dataset or claim representative review quality.

To upgrade an existing source installation, check out the desired Vee revision and rerun `cargo install --path crates/vee-cli --locked --force --root "$HOME/.local"`. The SQLite database and artifacts in each repository's `.vee/` directory are retained; Vee applies storage migrations when opening the database. Back up `.vee/` before upgrading if it contains review history you cannot recreate. Vee is not yet published as a crates.io package; source installation is the supported distribution path for this release candidate.

## Performance baseline

`python3 scripts/benchmark-review.py --vee target/debug/vee` measures whole-process review latency on temporary Git repositories with a deterministic local fake provider. By default it reports small, medium, and large strata (100/5, 1,000/25, and 5,000/100 tracked/changed source files). Repeat `--matrix REPO_FILES:CHANGED_FILES` to customize strata; adjust `--lines-per-file`, `--warmups`, and `--iterations`, and use `--output baseline.json` to retain the versioned JSON result. The checked-in [2026-11-14 baseline](docs/performance-baseline-2026-11-14.json) records five measured runs per size after one warmup. This baseline covers local CLI, Git, storage, and fake-provider process overhead only. It does not measure AI quality, network latency, token use, or provider cost, and it sets no pass/fail latency target.

### Setup

Run `vee init` in a Git repository. It detects the AI backends on this machine, in this order of preference, and configures the first one it can use without further input:

1. a local Ollama model (loopback only; `OLLAMA_HOST` is honored when it points at this machine),
2. an installed coding-agent CLI: Codex, Antigravity (`agy`), Claude Code, or the deprecated Gemini CLI (reusing their existing login),
3. a vendor API key: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or `GEMINI_API_KEY` (choose with `--provider openai-api|anthropic-api|gemini-api --model <model-id>`).

In a terminal, `vee init` asks instead. It lists the backends it found, suggests a model for each where one is known to review best, and asks for the review effort: `low` runs each reviewer once, `medium` three times and `high` five times, and only findings that a majority of runs report can block. Enter accepts each recommendation. The choices are written to this machine's user config, and running `vee init` again on a set-up machine changes only the effort. `--provider`, `--model`, `--effort` or `--no-input` skip the questions, and so does a non-terminal session. [Getting the best reviews](docs/guides/best-results.md) explains the choices with Vee's benchmark results.

`vee providers detect` lists what was found. `init` writes `.vee.yaml` with a `correctness` reviewer and `.vee/reviewers/correctness.md`, and writes the machine-specific provider as `default` in the user config (`$VEE_CONFIG`, else `~/.config/vee/config.yaml`), so the repository config stays portable: each teammate runs `vee init` once to configure their own backend. `vee doctor` (MCP: `check_setup`) reports whether each configured reviewer can run here (version probe for CLIs, model presence for Ollama, key presence for APIs; no tokens are spent) and exits 0 when ready, 2 when not, with next steps. Vendor API keys are forwarded only to their vendor's HTTPS host (`api.anthropic.com`, `generativelanguage.googleapis.com`); `OPENAI_API_KEY` is also accepted for self-hosted OpenAI-compatible servers.

Add a provider under `providers` and a reviewer under `reviewers` in `.vee.yaml`; reviewer instructions are read from the named file. The repository config follows [repository-config-v1.schema.json](schemas/repository-config-v1.schema.json). `review.max_concurrency` controls bounded parallel reviewer runs (default 4, range 1–32). Per reviewer, context is bounded by `max_context_files` (default 512, max 2048), `max_context_file_bytes` (default 128 KiB, max 4 MiB), and `max_context_bytes` (default 512 KiB, max 16 MiB). Raise these limits when reviewing large implementation files; for example, 1 MiB per file and 4 MiB total. It sends complete baseline and current contents when every changed file fits. Otherwise it first reserves a bounded unified diff (40 lines of surrounding context) for each changed file, in path order, then upgrades diffs to complete contents with the remaining budget, smallest increase first, so a few large files cannot crowd the rest of the change out. Binary and Git LFS files use budget only for the text actually sent. If a file or diff is omitted by these limits, the reviewer outcome is `context_limited` and the gate is incomplete. For a provider with a known input window, set `providers.<id>.max_input_tokens` (1,024–131,072). Vee estimates the serialized prompt size, drops lowest-priority impact source text first, keeps omitted paths visible as metadata, and marks that reviewer incomplete. If changed-source context alone exceeds the budget, Vee skips the provider call and records `context_budget_exceeded`. The estimate is approximate and does not replace provider-reported token usage. With `review.exploration.enabled: true` (off by default), a `claude_cli` reviewer can also read more of the review snapshot through three read-only tools that Vee serves itself: `list_files`, `read_file` and `search` ([ADR 0017](docs/adr/0017-reviewers-explore-the-review-snapshot.md)). Changed files are read from the captured snapshot and unchanged ones from the captured head tree, never from the working tree, untracked files or paths outside the repository. Review `include`/`exclude` apply, and environment files, private keys and credential stores are never readable; `review.exploration.deny` adds globs to that list. Each reviewer request may make `max_tool_calls` calls (default 24, max 200) and read `max_read_bytes` (default 256 KiB, max 4 MiB). The reviewer context manifest records the calls, bytes and files each reviewer read. Other providers review the supplied context alone and record exploration as `unsupported`. Repository-wide `review.include` and `review.exclude` globs apply first. Each reviewer can further narrow its context with its own `include` and `exclude` globs; exclusions win and an empty reviewer `include` inherits all repository-included paths. `kind: ollama_native` connects directly to a local Ollama `/api/chat` endpoint, sends the configured `context_window_tokens` as `options.num_ctx`, samples with temperature 0 and a fixed seed so repeated reviews of the same request agree, uses schema-constrained JSON output, and records Ollama prompt/eval token counts. It requires `egress: local`, a loopback HTTP endpoint, and `max_input_tokens`; `max_output_tokens` optionally raises or lowers its 2,048-token default, and the input plus output budgets must fit in `context_window_tokens`. This makes the requested window explicit instead of relying on the Ollama server default. `kind: openai_compatible` selects an HTTP Chat Completions adapter with schema-constrained output, bounded response size, timeout, cancellation, no redirects, and no proxy environment use. Configure an explicit `endpoint`, `model`, and `egress`; `egress: local` accepts only localhost or loopback IPs and can be used with `offline: true`. Hosted endpoints must use `egress: network`. `OPENAI_API_KEY` is sent only when included in `env_allowlist`; it is the only environment variable accepted for this adapter. Credentials are not stored in YAML. Context is sent to the configured endpoint, so local execution alone does not imply offline inference. API responses are not cached yet. Set `providers.<id>.timeout_seconds` (default 120) for slower local models. Diagnostics distinguish connection failures and timeouts from common HTTP request, context-size, authentication, rate-limit, and server errors; provider error bodies are omitted so they cannot echo repository text or credentials. `kind: codex_cli` selects Vee's Codex-specific read-only contract. It runs `codex exec --json` with ephemeral state, ignores user config, skips the Git repository check because Vee supplies captured context from an isolated temporary directory, uses `--sandbox read-only`, passes a temporary output schema, and sends the review prompt on stdin. Vee extracts the final structured assistant message and provider-reported input/output token counts from JSONL events; it does not retain cache subtotals or infer a total. `kind: antigravity_cli` selects Google's Antigravity CLI (`agy`) print mode with `--output-format json` and the findings schema via `--json-schema`; Vee extracts `structured_output` and reported input/output/total token counts. `agy` has no read-only switch and its print mode applies edits by default, so Vee pins `--mode plan`, `--sandbox` and `--disable-slash-commands`, and runs it in an empty temporary directory. Sign in once by running `agy` interactively; an unsigned headless run fails after about a minute with a sign-in hint. The Antigravity and Gemini CLIs take the prompt as a command-line argument, so a review request over 100,000 bytes fails before the CLI starts (Linux allows at most 128 KiB per argument); narrow the change or `review.max_context_bytes`. The Claude CLI adapter sends the prompt on stdin and has no such limit. `kind: gemini_cli` selects Gemini CLI headless mode (`--prompt`, `--output-format json`); Vee extracts only the envelope's `response` and validates it as findings JSON. Google deprecated Gemini CLI in June 2026 in favor of Antigravity; the adapter remains for existing setups. `kind: claude_cli` selects Claude Code print mode with restricted mode, no session persistence, no built-in tools (with exploration on, only Vee's snapshot tools through `--strict-mcp-config`), and schema-validated JSON output; Vee extracts `structured_output` and reported input/output token counts. Cache token subtotals and reported cost are not retained. All provider-specific adapters own their arguments and probe `--version`. Do not configure custom args or version args for them. Their review prompts prohibit edits and command execution; Claude’s restricted mode also disables command tools. These providers may still have network access and use external inference; set `egress: network` and use trusted CLI configuration. `kind: cli` remains available for generic executables that accept Vee's JSON request on stdin and return provider-findings-v1 JSON on stdout. A generic provider can declare `version_args` (for example `[--version]`) so Vee can capture its version with a bounded probe; without this declaration its version is reported as unknown. For example:

```yaml
review:
  max_concurrency: 4 # bounded reviewer parallelism; allowed range 1..=32
  include: ["**/*.rs", "**/*.go"]
  exclude: ["**/generated/**"]
providers:
  codex:
    kind: codex_cli
    egress: network
    executable: codex
    model: gpt-5-codex # optional
    env_allowlist: [PATH, HOME, CODEX_HOME]
reviewers:
  correctness:
    provider: codex
    instructions_file: .vee/reviewers/correctness.md
    context_files: [docs/architecture.md]
    include: ["src/**/*.rs"]
  security:
    provider: codex
    instructions_file: .vee/reviewers/security.md
    exclude: ["**/*_test.rs"]
```

Small local models often return no findings when the whole change arrives in one request. For an `ollama_native` provider, set `strategy: focused` on the reviewer to review each changed file separately: Vee first asks for free-text reasoning over line-numbered source with changed lines marked, then asks for structured findings. Each finding quotes the faulty changed statement, and Vee resolves that quote to a line number itself; a quote it cannot match to exactly one changed line leaves the line empty. Focused review makes two requests per changed file, so it takes longer and uses more tokens than the default `whole_change`. Use reviewer `exclude` globs to leave out test files when that time matters. Impact-reference files are not sent in focused mode; other changed non-test files are added as related context while they fit the context window. Focused review makes a small local model useful, but it does not match a strong hosted reviewer: on Vee's local historical-defect benchmark it recalled far fewer labeled defects and took minutes per change instead of seconds ([results](docs/local-historical-review-benchmark.md), [ADR 0007](docs/adr/0007-focused-review-strategy.md)). The `max_input_tokens` budget applies to the largest single focused request, not to the whole change. Rule attributions are limited to approved guidance whose scope covers the file under review.

While a review runs, each transport shows which reviewer runs have finished: `vee review` redraws one progress line on stderr when stderr is an interactive terminal and the output is text (pipes, logs, and `--output json` stay clean); MCP `review_changes` sends `notifications/progress` with the same summary to clients that pass a `progressToken`, and `start_review` tasks carry it as their status message; the dashboard shows each reviewer's state.

When a provider reports a usage, quota, or rate limit (an HTTP 429, or an agent CLI's "usage limit" message on a non-zero exit), Vee skips that provider's remaining runs in the review instead of letting each fail the same way; those reviewers and the one that hit the limit are recorded as `rate_limited`, the review is incomplete, and the queue suggests rerunning them. Other providers keep running.

Set `advisory: true` on a reviewer to show its findings without letting them block the gate; a finding that a non-advisory reviewer also reports still blocks. `vee init` adds an advisory `architecture` reviewer for layering, coupling, duplication and other design problems the change introduces. It is disabled by default because it doubles provider calls and its instructions are not yet benchmarked; set `enabled: true` to use it. See [ADR 0009](docs/adr/0009-advisory-reviewers-and-analyzer-split.md). `vee init` also adds an advisory `task-alignment` reviewer, off by default, that checks whether a change does what its work item asks and nothing more: a missing requirement, a change the task does not ask for, or one that contradicts it. It reads the work item that `vee review --work-item OWNER/REPO#NUMBER` attaches, as untrusted requirements text, and reports nothing without one.

A single model review is a sample: on Vee's historical-defect benchmark, three identical runs of the same hosted reviewer found different defects. Set `effort: medium` on a reviewer to send the request three times (`low` runs it once, the default; `high` five times), or run `vee review --effort high` to raise every reviewer's effort for one review. `samples: N` (1–5) sets the count exactly. Vee merges the runs by location (same file, lines at most three apart), and each finding records how many runs reported it in `sample_agreement`. A finding blocks the gate only when at least `sample_quorum` runs reported it (default: a strict majority); the rest are shown as advisory. Sampling costs one provider call per sample. Runs proceed concurrently within `review.max_concurrency`. If any run fails, the reviewer fails and the review is incomplete. Sampled Ollama runs use temperature 0.8 with distinct fixed seeds; unsampled Ollama reviews stay at temperature 0. A generic `kind: cli` provider receives the same request for every sample, plus `VEE_SAMPLE_INDEX` (from 0) and `VEE_SAMPLE_COUNT` in its environment so it can vary its own sampling. See [ADR 0008](docs/adr/0008-reviewer-sampling.md).

Provider defaults can also live in a per-user `config.yaml`: `$XDG_CONFIG_HOME/vee/config.yaml` (or `~/.config/vee/config.yaml` when XDG is unset) on Unix-like systems, and `%APPDATA%/vee/config.yaml` on Windows. Set `VEE_CONFIG` to use a specific file. This file uses [user-config-v1.schema.json](schemas/user-config-v1.schema.json) and may define `version: 1` plus `providers`; repository provider entries override same-ID user entries. This lets a checked-in reviewer refer to a provider configured on the developer's machine. Effective merged provider settings participate in the review digest. Keep credentials outside both config files: use environment variables named by `env_allowlist` or an OS secret store.

Use a reviewer's optional `context_files` list to provide bounded, unchanged repository files that help explain the changed code, such as an architecture note or related interface. Vee confines these paths to the repository, marks their contents as untrusted source, and includes their content digests in the effective review configuration. Editing a listed file makes an earlier gate stale; changing it while review is running makes that run incomplete. Files over the configured context limits are omitted and mark that reviewer's context incomplete. These files are sent to the selected provider under its configured egress mode; `egress: local` classifies the provider but does not enforce operating-system network isolation.

Vee reuses a successful reviewer response only when the complete request, provider version, executable content, model, arguments, limits, and allowlisted environment-value digest match. Providers without a declared or probed version are never cached. Failed and invalid responses are not cached. Cached outcomes are reported as `cached` and count as completed reviewers. Allowlisted environment values are hashed into review freshness identity, so changing a credential or endpoint invalidates the previous gate without writing the value to storage.

Use repeated `--reviewer <id>` flags to run only selected enabled reviewers, for example `vee review --base main --reviewer correctness --reviewer security --gate`. Without flags, every enabled reviewer runs. Selection is recorded in the review and included in its effective configuration digest; leaving a policy-required reviewer out makes the analysis incomplete. MCP `review_changes` and `start_review` accept an optional `reviewer_ids` string array with the same semantics. The generic provider receives one JSON document on stdin with snapshot ID, reviewer ID, instructions, and changed paths. Providers run from an empty, disposable working directory, so relative file access does not expose or modify the repository. A configured executable containing a relative path is resolved against the repository before the working directory changes. This is defense in depth, not an OS sandbox: a provider running as the current user can still access absolute paths and use any explicitly allowed environment values. Configure required environment variable names with `env_allowlist`; Vee resolves values from the invoking process, clears other inherited values, and does not persist the values. Vee invokes executables without a shell. Provider `egress` defaults to `network`; set `offline: true` at the configuration root to reject network providers during configuration validation. To force offline behavior for one invocation regardless of repository configuration, set `VEE_OFFLINE=1` (also accepts `true`, `yes`, or `on`). This override only strengthens offline mode; false values do not weaken repository `offline: true`. A generic executable must be declared `egress: local` to be accepted in offline mode. That declaration classifies the adapter but does not provide OS-level network isolation; only use it for a provider you have configured to run locally. The Codex CLI adapter is always classified as network-backed. See the [Codex CLI non-interactive mode documentation](https://learn.chatgpt.com/docs/non-interactive-mode) for its `exec` contract.

Reviewers may be limited with `include` and `exclude` globs. A changed file that passes `review.include`/`review.exclude` but that no reviewer received is listed as **not reviewed** in the review output (`unreviewed_paths`), the Markdown report and the UI. By default (`policy.on_unreviewed: block`) such a file leaves the analysis incomplete, so the gate cannot pass on code no reviewer read; set `on_unreviewed: allow` to report it only. Packs and the protected policy can only tighten this setting. See [ADR 0010](docs/adr/0010-unreviewed-changes-leave-the-gate-incomplete.md).

Named policy profiles can be defined under `policy_profiles`; each profile uses the same fields as `policy` and is selected with `vee review --policy-profile strict`. The chosen profile is stored in the review and restored by `gate check`. MCP `review_changes` and `start_review` accept the optional `policy_profile` field. The trusted local `.vee/policy.yaml` is applied after profile selection, so a profile cannot weaken protected requirements. Reviewer definitions may also add reviewer-specific `policy.block_severities` and `policy.minimum_confidence` rules. These rules add to the global gate: a finding blocks if it meets the repository policy or a policy for any reviewer listed in its `reviewer_ids`; a reviewer rule cannot override or weaken global policy. Example: `security: { policy: { block_severities: [critical], minimum_confidence: 30 } }`. The effective policy digest binds these rules and reviewer attribution.

Every reviewer writes findings to the same rubric, whichever provider runs it. A finding reports one defect, led by what goes wrong. Severity follows the defect's consequence: `critical` for a security breach or data loss, `high` for a wrong result or crash on a normal path, `medium` for one that needs a specific but realistic input or state, and `low` for a minor effect. The rubric is part of Vee, not configuration, so `block_severities`, packs and gate attestations mean the same thing in every repository. To raise the bar where it matters, add `policy.severity_floors`:

```yaml
policy:
  block_severities: [critical, high]
  severity_floors:
    - paths: ["payments/**", "billing/**"]
      minimum: high
    - categories: [security]
      minimum: high
```

A floor applies to findings that match one of its path globs, one of its categories (compared case-insensitively), or both when both are set. The gate evaluates the higher of the reported severity and every matching floor, for the repository policy and for reviewer policies. The review record keeps the reported severity, and a gate that blocks because of a floor names the finding, both severities and the floor. Floors from packs and from `.vee/policy.yaml` are added to the repository's floors and cannot be removed. See [ADR 0018](docs/adr/0018-fixed-finding-rubric-and-severity-floors.md).

For repositories where policy must not be weakened by checked-in configuration, maintainers can provide a trusted local `.vee/policy.yaml`. It can add required reviewers and verification profiles, add blocking severities, lower the confidence threshold at which findings block, add severity floors, and require incomplete analyses to block. Repository config may strengthen these settings, but cannot weaken them. Requirements must name reviewers and verification profiles already declared in `.vee.yaml`; malformed protected policy fails configuration. The merged effective configuration is fingerprinted, so edits invalidate prior gate approvals. Keep this file in the local checkout's `.vee` directory and provision it through the repository owner's trusted setup process.

Shell completions: `vee completions <bash|zsh|fish|elvish|powershell>` prints a completion script to stdout, for example `vee completions zsh > ~/.zfunc/_vee`.

Every command that takes `--output` defaults to human-readable `text`; pass `--output json` for one compact, versioned JSON document on stdout. Each JSON document is the same one the matching MCP tool returns, and both are validated against the published schemas in `schemas/`. Text output is the same view the matching MCP tool returns as Markdown: findings are ranked with blocking ones first, statuses carry a symbol as well as a color, and each result ends with the next command to run. `--color auto|always|never` controls color (default `auto`: only on a terminal, honoring `NO_COLOR`, `CLICOLOR` and `CLICOLOR_FORCE`). Text output is for people; scripts should use `--output json`. MCP tools return that view as Markdown text content and the full JSON document as `structuredContent`; tools without an output schema still return JSON text. See [ADR 0011](docs/adr/0011-shared-presentation-for-cli-and-mcp.md).

Exit codes: `0` pass (and top-level help/version), `1` block, `2` incomplete or execution failure, `3` usage/configuration failure. JSON output is one versioned document on stdout; review summaries and diagnostics go to stderr. JSON errors use the versioned `cli-error-v1` schema and identify `usage_error`, `configuration_error`, or `execution_failed`.

Use `vee review --markdown /tmp/review.md` to write a portable Markdown report alongside the normal text or JSON stdout result. It includes the gate decision, reviewer outcomes, findings, locations, provenance, and evidence references. Provider/model text is escaped as Markdown content. If you save the report inside the checkout, Git may treat it as a source change and make a later gate recheck stale; place it outside the checkout or in an ignored path.

`gate check` reloads the stored review, recaptures its recorded Git scope, recomputes the effective config and reviewer-instruction digest, and rejects the decision as incomplete if either source or review inputs changed. `.vee.yaml` is excluded from the source manifest and fingerprinted in effective configuration separately. Gate decisions and gate-check responses expose the effective configuration digest separately from the policy digest, and the decision identity binds both. Gate-check JSON follows [schemas/gate-check-v1.schema.json](schemas/gate-check-v1.schema.json).
`vee gate history --review <review-id> --output json` lists immutable gate decisions recorded for that review, including rechecks after verification evidence changes.
Use `vee reviews list --output json` to find persisted reviews and `vee reviews show <review-id> --output json` to retrieve the full record. The list response follows [schemas/reviews-list-v1.schema.json](schemas/reviews-list-v1.schema.json); review output v2 records reviewer provider ID, adapter kind, configured model, probed Codex CLI version, and optional adapter wall-clock duration in addition to status. Its `reviewer_context` manifest records per-reviewer changed paths as full source, bounded diff, metadata only, filter excluded, or omitted by context limits, with a digest for each supplied artifact and no duplicate source text. Duration is absent for cached responses and when no adapter invocation occurred. Publish a saved review to GitHub, GitLab, Bitbucket Cloud, Azure DevOps or Gerrit with `vee hosting publish --provider <github|gitlab|bitbucket|azure-devops|gerrit> --review <review-id> --repository workspace/repo --number <pr-id>`. GitHub/GitLab accept `--actor-login`; Bitbucket obtains the authenticated actor identity from its API. For GitHub, check-run publication requires a GitHub App user or installation token with **Checks: write**; inline review comments require **Pull requests: write**. A personal access token cannot create GitHub check runs, so use a GitHub App credential for Vee's combined check-and-comment publication flow ([GitHub Checks API requirements](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks), [pull request review permissions](https://docs.github.com/en/rest/pulls/reviews)). When GitHub rejects a request, Vee reports its bounded API message and, when supplied, the `X-Accepted-GitHub-Permissions` requirements; credentials and control characters are excluded from that diagnostic. Azure DevOps supports gate status publication with `--provider azure-devops --repository organization/project/repository`; set `AZURE_DEVOPS_EXT_PAT` or pass `--token-env`. Azure DevOps status publication is bound to the current PR base/head revision and uses the stable Vee status context for retry-safe updates. Finding threads are posted only when the saved finding path and line match an added line in the local base-to-head Git diff. Azure iteration metadata binds each comment to the active PR iteration. New comments include per-review idempotency and stable finding fingerprint markers. Vee verifies the initial comment author against Azure DevOps’ authenticated identity before refreshing its content or changing thread status; resolved findings close a matching Vee thread, and a recurring finding reopens it. Reviewer-authored threads are left untouched. Gerrit receives one tagged review per publication: a message with the gate decision and inline comments on the change's current revision, marked unresolved while the finding is open and resolved when it is fixed. Gerrit has no separate check, so `--approval` is refused there and no label is voted; set `GERRIT_TOKEN`, and pass `--username` when the token is an HTTP password for Basic authentication. Bitbucket Cloud publishes commit build status and fingerprinted inline comments; it verifies comment authorship against the authenticated account and uses Bitbucket's native resolve/reopen API for matching Vee comments. Set `GH_TOKEN`, `GL_TOKEN`, or `BB_TOKEN` with the required provider status and pull request comment permissions. GitLab uses its commit status and merge request discussions APIs; its MR revision and diff reads are bound to `diff_refs`. The command checks the current PR head against the reviewed commit, refuses staged-only, working-tree-only, or dirty snapshots, and posts inline comments only where the finding line is an added line in the PR diff. Self-hosted GitHub Enterprise uses `--host <hostname> --api-base https://<hostname>/api/v3/`. Vee sends a hosting credential only to the provider's public service or to a host you name: with `--host` or `--api-base`, or in `VEE_HOSTING_HOSTS` (comma-separated, for example `VEE_HOSTING_HOSTS=git.example.com` in CI). A host set only in `.vee.yaml` is refused, because the repository configuration can come from any branch. For the same reason, `.vee.yaml` may name only hosting credentials in `hosting.token_env` and `hosting.webhook_secret_env` (`GH_TOKEN`, `GITHUB_TOKEN`, `GL_TOKEN`, `GITLAB_TOKEN`, `CI_JOB_TOKEN`, `BB_TOKEN`, `BITBUCKET_TOKEN`, `AZURE_DEVOPS_EXT_PAT`, `SYSTEM_ACCESSTOKEN`, `GERRIT_TOKEN`, or any `VEE_` variable); pass any other variable with `--token-env` or `--webhook-secret-env`.

Run a hosting webhook receiver with `vee hosting webhook-serve --provider <github|gitlab|bitbucket|azure-devops|gerrit> --repository <provider-specific-path> [--actor-login <bot-login>]`. GitHub reads `GH_TOKEN` and `VEE_GITHUB_WEBHOOK_SECRET`; GitLab reads `GL_TOKEN` and `VEE_GITLAB_WEBHOOK_SECRET` (GitLab signing tokens use its `whsec_` format); Bitbucket reads `BB_TOKEN` and `VEE_BITBUCKET_WEBHOOK_SECRET`; Azure DevOps reads `AZURE_DEVOPS_EXT_PAT` and `VEE_AZURE_DEVOPS_WEBHOOK_SECRET`; Gerrit reads `GERRIT_TOKEN` and `VEE_GERRIT_WEBHOOK_SECRET`. The webhook server exposes only the configured provider's webhook path and `/api/health`: no UI, review or configuration API, since it may sit behind a tunnel or proxy. Other paths return 404. Request bodies are capped at 1 MiB before signature verification and parsing. Bitbucket verifies `X-Hub-Signature` as HMAC-SHA256 over the raw request body and uses `/api/webhooks/bitbucket`. Gerrit verifies `X-Gerrit-Signature: sha256=...` over the raw body at `/api/webhooks/gerrit`; its standard webhook plugin does not document signed payloads, so configure an HMAC-signing relay or signing reverse proxy; Vee rejects Gerrit relay secrets shorter than 32 bytes. `--actor-login` is required for GitHub and GitLab, where Vee must identify its own comments. For Azure DevOps, use `--repository organization/project/repository`, configure the Service Hook URL as `/api/webhooks/azure-devops`, and set its Basic-auth password to the Vee secret. Azure PR created and active source-update events are reviewed; close and updates without usable revisions are acknowledged without review. Gerrit `patchset-created` and `change-restored` events trigger review only when the signed event's patch-set SHA still matches Gerrit's live current revision. The listener reviews only exact commit ranges already present locally and still matching the current open PR/MR. It stores the review, publishes a Vee status/check, and posts inline comments for findings on added diff lines. Superseded events are acknowledged; missing local commits return a retryable failure until an operator makes them available. Vee currently accepts loopback bindings only because its HTTP server does not terminate TLS. Keep webhook listeners on loopback and, when external delivery is required, place a same-machine TLS-terminating reverse proxy in front of that listener. Use HTTPS for Azure Basic authentication. `--allow-network` is reserved and does not enable plaintext network access. The signed webhook route does not use a browser token. Vee does not fetch untrusted PR commits automatically.

Webhook delivery receipts can be pruned with `vee hosting prune-webhooks --older-than-days 90`. The command previews eligible completed receipts by default; add `--apply` to delete them. In-flight and retryable deliveries are retained. Removing an old receipt also removes its duplicate-delivery protection, so choose a retention period that matches the provider's retry and replay window. Export an auditable evidence package for the latest gate decision with `vee reviews bundle <review-id> > evidence.json`, or select one with `--decision-id <decision-id>`. ## Impact analysis

Map package dependencies among explicitly selected local checkouts with `vee repos map path/to/repo-a path/to/repo-b --output json`. The mapper reads Cargo package, npm `package.json`, and Go `go.mod` manifests, reports direct dependencies that match another supplied package, and binds each edge to its source manifest digest. Cargo workspace member paths and one-level `*` patterns are expanded, `workspace = true` constraints are resolved and bound to both member and workspace manifest digests, and local path dependencies are matched by canonical package root. Edges retain declared requirements, identify whether matching used a resolved path, package name, or npm alias, and report Cargo semver compatibility plus npm compatibility for supported semver ranges against the selected local package version. npm aliases retain their declared dependency key while resolving the `npm:` target package name. Go local filesystem `replace` directives are followed only when their path resolves to one of the explicitly selected repositories; remote or otherwise unsupported replacement targets are reported as limitations and their dependency edges are omitted so the unreplaced module is not mistaken for the actual target. `go.work` resolution is not followed. For Go, an incompatible requirement major versus the selected module path's `/vN` or `gopkg.in/...vN` suffix is reported; a matching major remains `not_evaluated` because the selected module version is not resolved. Unsupported npm protocols remain unevaluated; Go version selection, lockfiles, and transitive dependencies are not analyzed. Ambiguous matches are omitted and reported. Unsupported repositories and members are listed as limitations rather than treated as dependency-free. JSON follows [repository-map-v2.schema.json](schemas/repository-map-v2.schema.json); v1 remains available for prior consumers and includes an overall deterministic map digest.

`vee reviews session --review A --review B ...` reads up to 20 saved reviews together, such as the commits or branches one coding-agent session produced. Each change keeps its own gate, risk tier, open findings by severity, and approval eligibility; the session verdict is `block` when any change blocked, `pass` only when every change passed on a snapshot that has not moved since its review, and `incomplete` otherwise. Like the gate, it exits 0 on `pass`, 1 on `block`, and 2 on `incomplete`; repeated review IDs are a usage error (exit 3). MCP exposes the same document as `review_session`; JSON follows [schemas/review-session-v1.schema.json](schemas/review-session-v1.schema.json). A review saved in another checkout is named `REPO:REVIEW_ID`, with REPO relative to this repository's root (for example `--review ../api:rev_…`); each change is read from its own repository's store and configuration. Over MCP, REPO must stay beneath the server's repository root.

`vee gate approval --review REVIEW_ID` checks whether a reviewed change may be approved without a human. It evaluates five stages in order and reports each with its reason: the checkout still matches the reviewed snapshot (otherwise approval is withdrawn), no changed path matches `approval.never_paths`, no commit author's name or email matches `approval.never_authors` (only the matching pattern is reported), the change-risk tier is within `approval.max_risk` (`low` by default, or `elevated`), and the gate passes when evaluated now (without recording a decision, so a verification run since the last `gate check` counts). Guards are not part of the effective configuration digest, so changing them never makes reviews stale. The command exits 0 only when every stage passes. MCP exposes the same document as `check_approval_eligibility`; JSON follows [schemas/approval-eligibility-v1.schema.json](schemas/approval-eligibility-v1.schema.json). See [ADR 0015](docs/adr/0015-layered-approval-eligibility.md). `vee hosting publish --approval` also publishes the verdict to the pull request as a separate `Vee approval` check, next to the gate's `Vee` check: success when eligible, neutral when a person is needed (Bitbucket shows neutral as stopped), with every stage in its summary. Automation such as auto-merge can key on that check's success; it is not available for Gerrit.

```yaml
approval:
  never_paths: ["migrations/**", "src/auth/**"]
  never_authors: ["*[bot]*"]
  max_risk: low
```

`vee risk --base main` reports a change's risk tier (`low`, `elevated`, `high`) from five measured factors, plus two history factors when there are at least 20 commits: code subsystems touched (documentation excluded), files changed, lines added and deleted, production files referencing changed code, changed source files with no test changed or referencing them, and, with at least 20 commits of history, earlier changes to and people who changed the touched code, flagged above the repository's own 90th percentile. Each factor shows its value, threshold, what was counted, and the research it comes from; the tier is a rule over flagged factors (none: low, one or two: elevated, three or more: high), not a calibrated probability, and it never changes the gate. The dashboard shows it as a summary card while the checkout matches the reviewed snapshot. MCP exposes the same document as `assess_change_risk`; JSON follows [schemas/change-risk-v1.schema.json](schemas/change-risk-v1.schema.json). See [ADR 0014](docs/adr/0014-change-risk-as-explained-tiers.md).

`vee impact --base main --output json` reports changed Go/Rust/TypeScript/JavaScript/Python/Java declarations, references, and source line evidence. Rust references are parsed from expression/type paths, imports, method calls, macro paths, and identifiers in macro arguments, so comments and string literals do not count; they remain syntax-derived rather than type-resolved. Rust references inside actual `#[test]` functions and `#[cfg(test)]` contexts are marked as likely test references, including inline tests in changed files. Go references use `gopls` semantic reference results when the exact live snapshot matches and the local executable is available; otherwise Vee labels the textual fallback as heuristic. TypeScript/JavaScript references use the project's TypeScript language service (`tsserver`) when available and the exact reviewed snapshot matches the live workspace. Install TypeScript with `tsserver` on `PATH`, or set `VEE_TSSERVER` to an absolute `tsserver` executable or `tsserver.js` path (the latter also needs Node.js on `PATH`). Automatic type acquisition is disabled; repository plugins are not enabled. If semantic resolution cannot run, Vee labels the lexical fallback as heuristic. Python references use the installed Python interpreter's standard-library AST pass when available; it parses captured snapshot text without executing repository code and labels edges as syntax-inferred, not type-resolved. If Python is unavailable or a file cannot be parsed, the affected paths use the bounded lexical fallback and the report records the limitation. Python AST analysis has a 15-second and 2,048-edge bound. Java references use a bounded lexical analyzer that excludes comments and strings and labels every edge as heuristic. Java test paths recognize `src/test/` and `*Test.java`/`*Tests.java` conventions. Impact also mines Git history before the change's base: files that changed together with a changed file in at least 3 commits and 30% of its commits, at twice the other file's base rate of change (ignoring commits that touch more than 30 files) are reported as `co_change` edges with `historical` certainty and the commit counts, up to 5 per changed file, and never between documentation files; these show coupling such as schemas or configuration that no code reference reveals. Every relationship is labeled, analyzer availability and tool version are reported, and the response includes known limits and a `coverage_complete` flag. Dynamic dispatch, generated code, unresolved project references, and runtime interactions are not modeled. JSON follows [schemas/impact-assessment-v4.schema.json](schemas/impact-assessment-v4.schema.json); v1–v3 schemas remain available for earlier reports.

For explicitly selected checkouts, `vee repos impact path/to/producer path/to/consumer-a path/to/consumer-b --base main --output json` derives changed symbols from the producer's merge-base snapshot, maps declared package dependencies, and scans Rust, Go, TypeScript/JavaScript, Python, and Java consumer source. Changed OpenAPI JSON/YAML files contribute operation IDs, routes, methods, and producer contract digests; AsyncAPI 2.x contributes publish/subscribe channel operations, while AsyncAPI 3.x contributes send/receive channel operations. Matching operation IDs in consumer source are heuristic references. When a base contract is available, Vee reports removed operations, changed or removed operation IDs, and newly required parameters, request bodies and inline request properties, removed response statuses and request/response media types, removed request `oneOf`/`anyOf` branches and added response branches as compatibility risks, including under nested properties, array items, `additionalProperties`, `not`, and paired `allOf` branches. Branch matching is structural, bounded local `$ref`s are expanded for these checks, and full composition semantics remain incomplete. Vee also reports removed inline response properties and response properties whose required guarantee was removed, with component paths. Compatibility checks cover requiredness, parameter type and format changes, explicit parameter serialization changes (`style`, `explode`, `allowReserved`, and `allowEmptyValue` only when present on both sides), enum narrowing, numeric range narrowing, and inline object-schema changes across nested properties and array items; request/response schema constraints beyond selected property/type checks, parameter schema constraints beyond the explicitly supported inline and matching single-media parameter-content cases (with declared content media-type changes reported explicitly), full schema-composition semantics beyond conservative, nonconflicting `allOf` object type/property/required-field merges, unresolved/external references, and runtime security protocol behavior remain unassessed; v5 evaluates that bounded `allOf` subset and reports changes to composition operators and branch shapes, and structural changes to referenced security scheme definitions, as compatibility signals. Effective security requirement changes (scheme and scope sets) are reported as compatibility signals, so baseline comparisons add a limitation and set `coverage_complete` to `false`; schema v5 reports per-operation analyzed and unassessed areas, so these results are signals for review, not a compatibility guarantee. Each reference is associated with the deepest selected package containing its file and carries any matching producer-to-consumer dependency paths, including every manifest digest along the route. Dependency traversal is capped at 50,000 path states and 10,000 emitted paths; hitting either bound makes `coverage_complete` false. References outside that selected graph are marked `no_declared_path` or `package_unresolved`; a same-name occurrence alone is not dependency evidence. Consumer source hashes and inventory, producer contract files, and selected consumer manifests are rechecked before returning. Rust matches use syntax-recognized function and method call sites but do not resolve types, aliases, or traits. Go optionally uses bounded `gopls` definition; TypeScript/JavaScript optionally uses bounded `tsserver` definition and confirms matches against changed producer files. Python and Java references remain lexical. AsyncAPI 2.x/3.x compatibility compares channel/action/operationId plus selected changes in inline or bounded single-local-reference message payload schemas; AsyncAPI 3.x also detects channel-address changes. Multi-variant and external message references, protocol bindings, full composition semantics, and runtime protocol effects remain unassessed and keep coverage incomplete. JSON follows [cross-repository-impact-v15.schema.json](schemas/cross-repository-impact-v15.schema.json); v1 through v14 remain available for earlier contracts.

MCP clients can call `analyze_cross_repository_impact` with a `base_ref` and `consumer_paths`. The producer is the repository root selected when the MCP server starts; consumer paths must be relative Git checkout roots beneath that directory. The MCP handler rejects traversal and symlink escapes and returns the same versioned report as the CLI.

Resolve advisory ownership with `vee owners --path src/parser.rs --path crates/vee-cli/src/main.rs --output json`. Vee selects the first regular `CODEOWNERS` file in GitHub's precedence order: `.github/CODEOWNERS`, `CODEOWNERS`, then `docs/CODEOWNERS`. Within that file, the last matching rule wins. Reports include owners, matching rule and line, file digest, deterministic report digest, and explicit unowned/no-file states; paths must exist inside the checkout. JSON follows [ownership-report-v1.schema.json](schemas/ownership-report-v1.schema.json). Ownership is routing context only and cannot satisfy reviewer requirements or approve a gate. Unsupported or malformed patterns are skipped and mark coverage incomplete; escaped whitespace, negation rules, inline comments, and organization-wide ownership administration are not supported.

`--commit <ref>` reviews one immutable commit against its first parent (or the empty tree for a root commit). `--commit <from>..<to>` reviews a range against its endpoint tree. Sources come from Git trees, independent of later worktree edits. Commit scopes can be passed to `review` and `impact`; gate rechecks recapture the same commit or range. MCP clients use `scope: "commit"` and pass the ref or range in `commit`.

## Finding lifecycle

Findings persist across reviews by fingerprint. Their status can be inspected and updated with a required rationale:

```sh
vee findings list --severity high --status open
vee findings show find_<id>
vee findings task find_<id> --output json
vee findings set-status find_<id> --status verified --reason "Confirmed against the source"
```

`vee findings task` creates a bounded, snapshot-bound agent task bundle with finding lifecycle and provenance, current-snapshot status, an exact-snapshot source excerpt, the diff hunk covering the flagged line when that line is part of the change (`diff_hunk`, null otherwise), related impact paths, referenced evidence records, applicable standards, and advisory CODEOWNERS routing context. `vee findings package FIND_ID...` combines up to 20 such tasks only when they share the same review and snapshot; the package ID binds the ordered constituent task IDs. Repository source and standards are classified, returned context digests are verifiable, and impact/standards carry explicit limits. Ownership is advisory only and never grants authority or affects the gate. Neither task nor package authorizes edits or claims findings have been verified. JSON follows [finding-work-package-v2.schema.json](schemas/finding-work-package-v3.schema.json) and [finding-task-v3.schema.json](schemas/finding-task-v4.schema.json); [finding-work-package-v1.schema.json](schemas/finding-work-package-v1.schema.json), [finding-task-v2.schema.json](schemas/finding-task-v2.schema.json), and [finding-task-v1.schema.json](schemas/finding-task-v1.schema.json) remain available for earlier bundles.

An agent can prepare a unified diff and ask Vee to check it against the current reviewed tree:

```sh
vee findings propose-patch --review <review-id> /tmp/agent-change.patch
```

Vee rejects stale reviews and patches that do not apply cleanly, then stores the validated patch plus a digest-bound proposal record under `.vee/proposals/`. Apply only after reviewing the saved diff and explicitly approving its digest:

```sh
vee findings apply-patch sha256:<patch-digest> --approve sha256:<patch-digest>
```

Applying asks you to confirm at a terminal. Without a terminal, as in a coding agent's shell, it is refused unless your Vee user config sets `patches: { allow_noninteractive_apply: true }`, so an agent that may only propose a fix cannot apply it. A proposed patch may not change `.vee.yaml`, `.vee/`, CI definitions such as `.github/workflows/` or `.gitlab-ci.yml`, or Git hook directories; may not make a file executable; and may not leave a symlink pointing outside the repository. The CLI rechecks snapshot identity, effective review configuration, patch content, and applicability before applying, refuses replay, serializes concurrent Vee patch applications with a repository-local lock, and immediately reruns review with the saved scope and reviewer selection. Each proposal also records the touched paths’ preimage digests and the expected postimage from an isolated patch sandbox; apply rejects changed preimages and compares the applied files with that expected result. A staged review applies with `git apply --index` so the change remains in the staged scope. Immutable commit reviews cannot accept patches. The lock coordinates Vee processes, but external editor writes do not honor it, so a narrow race remains; Git hunk checks and post-apply comparison detect many such changes, and a detected mismatch returns incomplete while recording and rerunning the resulting snapshot. A stale lock fails closed and may be removed only after confirming no Vee patch application is running. The follow-up review and approval state are recorded in the proposal record, whose initial JSON follows [patch-proposal-v1.schema.json](schemas/patch-proposal-v1.schema.json); gate status maps to the regular `0` pass, `1` block, and `2` incomplete exit codes.

The show and JSON list outputs include occurrence history with review and snapshot IDs. Reobserving a resolved or waived finding reopens it; verified and refuted statuses remain intact for maintainer review.

For coordinated local changes across repositories, capture a deterministic change package:

```sh
vee repos package ./service ./shared-library --base main --output json
```

Pass `--discover-linked-prs` to find PRs from already-fetched local Git refs when a supported provider `origin` URL is configured. Discovery is offline and accepts only refs whose object ID exactly matches checkout `HEAD`; discovered links are identified separately from manually supplied links. Local refs can be stale, so use `--refresh-pr-links` with an explicit `--link-pr` to confirm current provider state.

The package also summarizes lifecycle across its linked PRs (`unrefreshed`, `partially_refreshed`, `mixed`, `all_open`, `all_closed`, `all_merged`, or `local_head_mismatch`) and reports per-state counts. This is coordination context only; it does not change local gate readiness.

The versioned package records each checkout's `HEAD`, branch, merge-base against the requested ref, snapshot ID, staged/unstaged/untracked and committed-since-base file digests, and direct local manifest dependency edges. Add `--link-pr REPO_ID=HOST/OWNER/REPO#NUMBER` for each linked provider change; repeat it to bind multiple PRs, including across providers. Links use validated provider-neutral identities, must refer to a repository in the package, and are included in the package digest. By default Vee does not fetch remote PR state. Use `--refresh-pr-links` to explicitly fetch each linked PR through the provider configured in that checkout’s `.vee.yaml`; the package records state, base/head OIDs, provider revision, and whether remote head matches local `HEAD`. This metadata is informational and is not gate evidence; refresh requires network access and the configured provider token environment variable. It reports a saved gate status only for an exact matching snapshot, with review, decision, policy, and effective-config identifiers. `gate_validity` rechecks the captured snapshot, effective configuration including protected policy, and deterministic replay against current snapshot-wide verification runs and waivers. A newer required verification result invalidates the older decision until `vee gate check` records the re-evaluated outcome. A review bound to an external work item is labeled `external_context_unverified`; package capture makes no implicit network request, so use `vee gate check` to re-fetch that context. Package `readiness` is `ready` only when every selected repository has a current passing gate, `blocked` when a current gate blocks, and otherwise `incomplete`. `priority_order` is a deterministic triage order based on current blockers, gate freshness, downstream selected repositories, changed-file count, then repository ID; factor details are included per repository. It is an explainable ordering, not a probability or SLA prediction. `not_reviewed` and `not_gated` remain explicit. Remote/transitive dependencies are not resolved. Direct selected Cargo package edges include a semver compatibility result; other ecosystems report version selection as unevaluated. See [change-package-v2.schema.json](schemas/change-package-v2.schema.json); v1 remains available for prior consumers.

Waivers are separate audit records and are bound to one finding fingerprint and one immutable review snapshot. They require a reason and author and expire after 30 days by default:

```sh
vee waivers create find_<id> --review rev_<id> --reason "Accepted until the next release" --author "maintainer" --expires-in-days 7 --output json
vee waivers list --review rev_<id> --output json
vee gate check --review rev_<id> --output json
```

The gate records applied waiver IDs in its evidence digest and explains which finding was waived. An expired waiver no longer suppresses a blocking finding. Any source change that produces a different snapshot makes the old review stale; create a new waiver against the new review if the exception still applies. The author is caller-supplied attribution, and the recorded provenance identifies the local CLI.

## Explicit verification

Verification profiles are repository-defined argument vectors and run only when explicitly selected. Vee invokes the configured executable directly, with no shell expansion, bounded time and output, and a null stdin. Results store the snapshot ID, command digest, exit status, and output digests in SQLite.

Each profile may declare `egress: local` or `egress: network`; omitted egress defaults to `network` for compatibility. `offline: true` rejects network-declared verification profiles as well as network-backed review providers. `egress: local` is a configuration assertion about the tool and its dependencies, not an OS network sandbox: for example, a package manager or test command may still attempt network access. Use tool-specific offline flags and OS network controls when strict isolation is required.

```yaml
verification:
  unit:
    executable: cargo
    args: [test, --workspace]
    env_allowlist: [CARGO_TERM_COLOR]
    timeout_seconds: 300
    output_limit_bytes: 1048576
policy:
  required_verifications: [unit]
```

Run a snapshot-wide profile with the same scope as the review, for example `vee verify --profile unit --base main --output json`; immutable commit reviews can be verified with `vee verify --profile unit --commit <full-commit-id> --output json`. To associate a check with a finding, pass its ID: `vee verify find_<id> --profile unit --output json`; Vee verifies the exact latest occurrence snapshot and rejects stale findings. Finding-scoped runs do not satisfy snapshot-wide required verification profiles. Inspect the saved record with `vee verification show <run-id> --output json`. Bounded stdout/stderr are stored as content-addressed files under `.vee/artifacts/sha256/`, referenced by the run and SQLite artifact index. Values from configured environment allowlists are redacted before hashing and storage. A passed command exits `0`, a completed command that reports a test failure exits `1`, and an incomplete or timed-out command exits `2`. Known offline Go module-lookup and Cargo offline-download diagnostics are classified as incomplete; other nonzero exits remain failed. Provider and verification configurations use `env_allowlist` variable names; Vee resolves values from the invoking process and clears all other inherited environment variables. Put credentials in the shell or OS secret store, never in `.vee.yaml`. Verification configuration contributes to the effective review configuration digest. Required profiles must have a latest successful result for the exact review snapshot. A newer failed or timed-out run makes the gate incomplete. Vee recaptures the selected source scope before and after each verification command and refuses to persist evidence if the snapshot is stale or changed during the command. Staged-scope verification also requires the checkout to match the index and have no non-ignored untracked files, because commands execute in the checkout. The gate output records the selected verification run IDs and their evidence digest.

The JSON contract is defined in [schemas/verification-run-v1.schema.json](schemas/verification-run-v1.schema.json). Artifact paths are relative to the repository root and content-addressed by their SHA-256 digest.

For profiles that emit LCOV to stdout or stderr (for example, a configured `cargo llvm-cov --lcov` invocation), list runs attached to an exact snapshot with `vee verification list --snapshot <snapshot-id> --output json` and summarize measured coverage with `vee verification coverage <run-id> --stream stdout --output json`. Vee verifies the saved artifact digest and immutable snapshot manifest before parsing. The report includes file-level executable-line coverage plus added/modified executable-line coverage when a bounded textual diff can be computed from the captured base and snapshot. It reports unknown when the baseline or diff is unavailable. Coverage is limited to the selected profile's execution and does not prove tests are adequate. JSON follows [verification-list-v1.schema.json](schemas/verification-list-v1.schema.json) and [coverage-report-v1.schema.json](schemas/coverage-report-v1.schema.json).

### Trusted analyzers (SARIF)

Any linter or security scanner that writes SARIF 2.1.0 to stdout can gate merges deterministically. Add a `sarif` section to its verification profile and require it:

```yaml
verification:
  semgrep:
    executable: semgrep
    args: [scan, --sarif, --quiet, --config, p/default]
    env_allowlist: [PATH, HOME]
    sarif:
      block_levels: [error]   # empty list = advisory
policy:
  required_verifications: [semgrep]
```

For vulnerable dependencies, secrets and known vulnerability patterns, run a security scanner the same way instead of relying on the AI reviewer. With nox:

```yaml
verification:
  nox:
    executable: nox
    args: [scan, ., --format, sarif, --output, "-", --offline, -q]
    env_allowlist: [PATH, HOME]
    sarif:
      block_levels: [error]
policy:
  required_verifications: [nox]
```

nox exits non-zero when it reports findings; with valid SARIF that is a complete run. Drop `--offline` to include OSV dependency advisories. Suppress accepted results with a nox baseline or a Vee waiver.

Run it on the same scope as the review (`vee verify --profile semgrep --base main`), then review with `--gate`. Only results located on lines added or modified in the snapshot count; pre-existing results never block. Results at a level listed in `block_levels` block the gate and appear in `blocking_findings` as `analyzer:<profile>:<id>`. A non-zero analyzer exit with valid SARIF is complete; a run that produced no valid SARIF makes the gate incomplete. Inspect a run with `vee verification findings <run-id>` (MCP: `get_analyzer_findings`), and waive an accepted result for one snapshot with `vee waivers create <analyzer-finding-id> --review <id> ...`. The derived reports are stored in the gate decision's replay inputs. JSON follows [analyzer-report-v1.schema.json](schemas/analyzer-report-v1.schema.json); see [ADR 0002](docs/adr/0002-trusted-analyzers-block-the-gate.md).

For Go repositories, a profile can opt into package-level test targeting from impact results by placing `{impacted_test_packages}` as a standalone argument, for example `args: [test, -json, "{impacted_test_packages}"]` with `executable: go`. Go targeted verification requires JSON package and individual-test pass events so a package where every test was skipped cannot be counted as tested. For Rust workspaces, use `{impacted_rust_test_filters}` with a Cargo test profile, for example `args: [test, --workspace, "{impacted_rust_test_filters}"]` and `executable: cargo`. Since Vee clears inherited environment variables, configure required names such as `PATH`, `HOME`, `CARGO_HOME`, and `RUSTUP_HOME` in each profile's `env_allowlist`. Run either with `vee verify --profile <profile> --impacted-tests --base main`. Vee expands Go targets to sorted, unique packages, or Rust targets to package-qualified test names and invokes Cargo with an explicit `--package` selection for each target. Changed Rust test files are included directly even when their tests have no impact-reference edges. It records the selected targets in the verification run and fails closed if impact coverage is incomplete, a Rust impact location cannot be mapped to a test function and package, no test target is found, or Go/Cargo reports success without running tests for every selected target. No shell interpolation is used. Targeted runs do not satisfy snapshot-wide required verification profiles.

## Provenance attestations

Export a gate decision as an in-toto attestation that supply-chain tools (Sigstore/cosign, SLSA policy engines, Witness, GUAC) can consume:

```sh
vee reviews keygen --private-key ci.pk8 --public-key ci.pub
vee reviews attest <review-id> --private-key ci.pk8 --key-id ci-2026 > gate.intoto.json
vee reviews verify-attestation gate.intoto.json --public-key ci.pub
```

The output is a DSSE envelope (`application/vnd.in-toto+json`) around an in-toto Statement v1 with predicate type `https://vee.klarlabs.de/attestations/review-gate/v1`. Its subjects are the reviewed snapshot digest and, only when the snapshot is exactly a commit's change (`--commit`, commit ranges, or a base review whose worktree matches the committed diff), the Git commit. The predicate records the decision, policy and configuration digests, reviewer outcomes, verification and analyzer results, and the evidence bundle's manifest digest. `--format statement` prints the unsigned statement for external signers; `--decision-id` attests a specific persisted decision. Formats: [review-gate-attestation-v1](schemas/review-gate-attestation-v1.schema.json) and [attestation-verification-v1](schemas/attestation-verification-v1.schema.json). See [ADR 0004](docs/adr/0004-gate-decisions-as-in-toto-attestations.md).

## Policy packs

A policy pack shares reviewers, gate policy, policy profiles, selected verification profiles, and approved rules across repositories. Export one from a repository that already has the setup you want, then pin it in others:

```sh
vee packs export ../packs/org-baseline --name org-baseline --version 1.0.0
vee packs add ../packs/org-baseline        # in each consuming repository
vee packs list                             # pinned packs and whether they still match
```

`vee packs add` copies the pack to `.vee/packs/<name>/` and pins its content digest in `.vee.yaml`:

```yaml
packs:
  - path: .vee/packs/org-baseline
    digest: sha256:…
    provider: default   # runs the pack's reviewers; `vee init` configures `default` per machine
```

Commit the pack directory with the pin. If the pack's files change, configuration loading fails (exit 3) until someone reviews the change and re-pins it (`vee packs add --replace <new version>`). Pack reviewers, verification profiles, and policy profiles are added, and repository definitions with the same ID win. Policy is merged so a repository can only tighten the pack: required reviewers, verifications, and blocking severities are combined, the lowest confidence threshold applies, and `on_incomplete: block` wins. Approved rules keep their original approver and reason. Verification profiles name repository-specific commands, so `export` includes them only with `--verification <id>`. Formats: [policy-pack-v1](schemas/policy-pack-v1.schema.json) (`pack.yaml`), [pack-summary-v1](schemas/pack-summary-v1.schema.json), and [packs-list-v1](schemas/packs-list-v1.schema.json) (also the MCP `list_packs` tool). See [ADR 0003](docs/adr/0003-policy-packs-pinned-and-tighten-only.md).

## Local investigation UI

Run `vee ui` from inside a checkout and open the printed `http://127.0.0.1:7878/#token=…` address. The token is generated for each run and is required on every API request, so other users and programs on the machine cannot read reviews, change configuration or start reviews; it travels in the URL fragment, which the browser never sends to the server, and the page keeps it for the tab. Vee currently accepts loopback bindings only; `--allow-network` does not enable direct LAN access until Vee can serve TLS itself. For remote access, use a secure local tunnel such as SSH port forwarding to the loopback listener. Stop the process when finished. The Vue interface lists saved reviews, starts branch/staged/working-tree reviews, and displays gate results, findings, reviewer outcomes, and evidence-backed impact paths. Each finding opens a details drawer with the reviewed snapshot's source around the finding (Vee keeps a content-addressed copy of each changed file with a located finding under `.vee/artifacts/sha256/`, so the source stays available after the file is edited), its evidence and verification runs, and a **Copy work package** action that copies the snapshot-bound `vee findings task` JSON for a coding agent. When a later review of the same scope and base commit exists, an older review links to it and marks the findings that review did not report again as **Outdated**; this is display only and does not change gates, dispositions or waivers. Insights can filter gate trends by reviewer, provider, finding category, approved-rule attribution, and inclusive custom date range over the latest 500 saved reviews; verification trends show bounded persisted run events by profile and date with snapshot-linked drill-down; provider Insights show current-rate cost estimates, daily history, and priced/unpriced usage coverage over the retained 2,000 reviews, and both JSON and CSV exports include filtered estimate metrics. Estimates require both token counts and an exact configured model rate, use current rates for retained historical usage, and do not affect gate decisions. Verification counts are run events, not test success rates. Severity and explicit feedback panels remain repository-wide current-record totals; rule-attributed counts use the latest bounded finding drill-down, and exports identify metric scopes. Rule attributions are reviewer-reported links constrained to active in-scope approvals, not verified causation. Filter dimensions are reported as incomplete when old review payloads cannot supply them. The review queue shows each review's next action, derived only from its latest gate decision and reviewer outcomes: rerun the reviewers that failed, fix the blocking findings, resolve the gate's first reason, or run `vee gate` when no decision exists. It is a triage pointer, not a merge recommendation. The analytics HTTP response follows [local-review-analytics-v10.schema.json](schemas/local-review-analytics-v10.schema.json); v9, v8, v7, v6, and v5 remain available as prior schema versions. A failed run of a SARIF analyzer profile also reports its findings on the changed lines, so Insights counts a clean scan as passed, matching the gate. Its configuration editor updates only `.vee.yaml`, and cannot change providers or verification profiles, which name programs Vee runs; edit those in the file itself; candidate settings are validated against provider/reviewer references and `.vee/policy.yaml` before an atomic replacement. User-level provider defaults remain in the user config and secrets remain environment-only. The bundled UI has no CDN or runtime network dependency. The HTTP API and CLI/MCP call the same `vee-application` services. Build its bundled assets with `cd web && npm ci && npm run build` before compiling the Rust workspace. Run the browser workflow suite with `cd web && npm ci && npx playwright install chromium && npm run build && npm run test:e2e`.

Run `vee mcp serve --transport stdio` inside a Git checkout to expose review operations to MCP clients. Tools include `review_changes` (`staged`, `working_tree`, `base` with a base ref, or `commit` with a commit ref), `start_review` (task-capable asynchronous review with status polling and cancellation), `list_findings` (filters and SQL-bounded pagination with a filtered `total` count), `get_finding` (including lifecycle and occurrences), `get_finding_task` and `get_finding_work_package` (bounded snapshot-bound single or same-review multi-finding agent context), `search_imported_review_history` (bounded search over imported findings and provider comments, explicitly untrusted and gate-ineligible), `record_external_review_feedback` and `list_external_review_feedback` (archive/revision-bound human labels for provider comments), `set_finding_status` (reason-required, bounded lifecycle disposition), `record_finding_feedback` (explicit accuracy/actionability label tied to a finding occurrence and snapshot), `list_rule_candidates`, `approve_rule_candidate` (requires a current evidence digest and explicit scope/instruction/provenance), `list_rule_approvals`, `revoke_rule_approval` (append-only audit event), `rule_effectiveness` (observational pre/post feedback report), `get_review`, `get_repository_context` (bounded path reads from an identified immutable review snapshot, with optional symbol-line matching, repository-root confinement, and untrusted-source labeling; follows [repository-context-v2.schema.json](schemas/repository-context-v2.schema.json)), `get_applicable_standards` (bounded, provenance-bearing standards resolution), `analyze_impact`, `verify_finding` (runs a configured verification profile only when the finding's source snapshot is still current), `check_setup` (setup diagnosis, same as `vee doctor`), `propose_patch` (validates and saves an agent diff as a digest-bound proposal; applying it stays a human `vee findings apply-patch` step), `recommend_tests`, `draft_pr_description`, `resolve_owners`, `list_waivers`, `get_gate_history`, and `evaluate_gate` (recaptures the reviewed scope, checks source and effective config freshness, reevaluates policy, and persists the decision). A lifecycle disposition is audit metadata; it does not waive a gate finding. Use the waiver workflow for a scoped exception with provenance and expiry. The response follows [finding-status-update-v1.schema.json](schemas/finding-status-update-v1.schema.json). The server uses pinned `klarlabs-mcp` 0.1.0. Stdio supports MCP 2026-07-28 discovery and explicitly negotiated legacy `initialize` clients; a clean-checkout tool-list/call path is tested for 2025-03-26. Legacy tool results use text content, while newer clients may receive structured content. Use synchronous `review_changes` with legacy clients; `start_review` requires modern task support. HTTP remains modern-only. The database is confined to the current checkout's `.vee/vee.sqlite`; clients cannot supply repository paths.

Every tool declares a title and MCP safety annotations so clients can auto-approve safe calls and confirm the rest. Read-only tools (`list_*`, `get_*`, `search_*`, `analyze_*`, `diagnose_verification`, `acceptance_traceability`, `rule_effectiveness`) set `readOnlyHint: true`. Tools that persist local records set `readOnlyHint: false`; `revoke_rule_approval` is marked destructive, and `review_changes`, `start_review`, and `evaluate_gate` are marked open-world because they may call network-backed reviewers or hosting APIs, depending on `.vee.yaml`. Input fields are documented in each tool's schema, and enumerated values (`scope`, `severity`, `status`, `label`) are declared as JSON Schema enums. Tools that share an operation with the CLI return exactly the document that the matching `vee ... --output json` command prints, and declare the published schema from `schemas/` as their `outputSchema`; the server validates every structured result against it and also returns it as a text block. Both transports call one shared operations layer, so validation rules, error messages, and staleness behavior are identical. The server sends `instructions` describing the review → investigate → verify → gate loop. Tool work runs on blocking worker threads, and a client cancellation of `review_changes` stops its reviewer subprocesses.

### Plugins for Claude Code and Codex

`plugins/vee/` packages Vee's MCP server and its six skills as one plugin for both agents. The plugin starts `vee mcp serve --transport stdio`, so install the `vee` binary on `PATH` first. For Claude Code, the plugin also has `SessionStart` and `Stop` hooks that review the agent's changes before it finishes ([daily use](docs/guides/daily-use.md)).

- **Claude Code:** `/plugin marketplace add klarlabs-studio/vee`, then `/plugin install vee@vee`. The skills run as `/vee:<skill>`, and the tools appear as `mcp__plugin_vee_vee__<tool>`.
- **Codex:** the repository marketplace at `.agents/plugins/marketplace.json` lists the plugin under Developer Tools. Its root `plugin.json` and `mcp.json` follow the portable Agent Plugins 1.0 format.

A test keeps the plugin's skills identical to the ones bundled in the binary, and its version equal to the crate version. `claude plugin validate .` checks the Claude Code marketplace.

### Coding-agent skills

`vee skills list` lists bundled portable agent skills. Run `vee skills install` from a checkout to install six skills under `.agents/skills/`: codebase context, standards retrieval, independent local review, finding investigation, finding resolution, and requirement traceability. Installation refuses existing files; `--force` replaces only the known `SKILL.md` targets. It refuses symlinked destination directories/files and writes only inside the current checkout. The skills use Vee CLI/MCP contracts and retain the rule that the coding agent—not Vee—makes authorized edits. They are plain Markdown and can be adapted for other agent skill-directory conventions.

`vee standards --path src/module/file.rs --output json` resolves applicable standards from root and ancestor `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`; root Copilot instructions; `.vee/policy.yaml`; `.vee/reviewers/*.md`; `.cursor/rules/*.mdc`; and `.claude/rules/*.md`. Output includes source content, digest, integrity state, scope, precedence, truncation, and potential same-tier conflicts. Precedence is protected policy (100), reviewer instructions (80), root/repository-wide guidance (50), remote standards (40), then nested agent instructions (60 plus directory depth, capped at 90). MCP `get_applicable_standards` calls the same resolver. An explicit `vee standards --sync-url https://standards.example/rules.md --source-id team-rules --source-scope 'organization engineering standard' --expected-digest sha256:<hex>` fetches one bounded HTTPS document into `.vee/standards-cache`; omitting the digest records `post-fetch-hash-only` and does not authenticate the publisher. `vee standards --remove-source team-rules` removes that source and its cached content. Redirects, URL credentials/query/fragment, non-HTTPS URLs, non-UTF-8 responses, and documents over 64 KiB are rejected; sync is blocked by `offline: true`. Remote content is guidance and never becomes protected gate policy. Reads are capped at 64 KiB per file, 128 files, and 256 KiB total; rule-directory discovery retains the 256 lexicographically earliest matching paths in bounded memory. Editor frontmatter globs and semantic contradictions are not interpreted, and these limitations are returned in the report. JSON follows [standards-resolution-v1.schema.json](schemas/standards-resolution-v1.schema.json).

`vee rules candidates --output json` mines repeated explicit human feedback by normalized finding category, including human-labeled archived provider comments. Three distinct finding fingerprints or external PR comments are required; contradictory labels on one source are excluded and counted. `false_positive` feedback suggests a narrowly scoped noise rule, while `not_actionable` suggests improving reviewer instructions or evidence quality rather than suppressing findings. Lifecycle state such as `waived` is not treated as a false-positive label. Each candidate retains up to five source examples with finding or provider-comment, archive, PR/revision, reviewer, and reason provenance. Candidate IDs and evidence digests are recomputed from the active source records at approval time, so changed or disputed feedback invalidates stale approvals. No suggestion changes policy or reviewer instructions without human approval. JSON follows [rule-candidates-v3.schema.json](schemas/rule-candidates-v3.schema.json).

Approve a current candidate only after writing the exact guidance and its scope with `vee rules approve CANDIDATE_ID --evidence-digest DIGEST --scope 'src/parser.rs' --instruction '...' --approver NAME --reason '...'`. Scope is a repository-relative file or directory path (no globs or parent traversal). Copy the digest from the candidate JSON; approval rejects a changed feedback digest. To replace guidance, pass `--supersedes APPROVAL_ID`; Vee retains both versions and the replacement receives the next version number. `--expires-in-days N` (1–3650) gives an approval a fixed expiry. Active guidance is appended to reviewer instructions only when a changed path matches its scope, and the active approval set is included in the effective configuration digest so activation, replacement, expiry, or revocation invalidates earlier decisions. Use `vee rules list` to inspect active, revoked, superseded, and expired guidance; `vee rules revoke APPROVAL_ID --actor NAME --reason '...'` appends a revocation event. `vee rules effectiveness [--approval-id ID]` compares explicit category-matched feedback before and after activation and retains the source feedback IDs/digest. The report is observational; it does not attribute changes causally to the guidance. MCP `approve_rule_candidate` accepts the equivalent `supersedes_approval_id` and `expires_in_days` fields. These records are advisory inputs only; they cannot override safety/output requirements or gate policy. `rules approve` and `rules revoke` JSON follows [rule-approval-v2.schema.json](schemas/rule-approval-v2.schema.json), and `rules list` JSON is an object whose `approvals` array holds those records ([rule-approval-list-v1.schema.json](schemas/rule-approval-list-v1.schema.json)); effectiveness output follows [rule-effectiveness-v1.schema.json](schemas/rule-effectiveness-v1.schema.json).

`vee tests recommend --base main --output json` uses the same snapshot-bound Go/Rust/TypeScript/JavaScript/Python/Java impact analysis to flag changed source files with no likely test-reference edge. Optionally add `--coverage-run <run-id>` to include a digest-verified LCOV artifact from a verification run bound to the exact same snapshot; Vee rejects stale runs. Recommendations report file-level and, when the captured diff is available, added/modified executable-line coverage. These are profile-specific signals and do not prove that tests are missing or adequate. The response carries impact coverage status, execution coverage when requested, and limitations. JSON follows [test-recommendations-v1.schema.json](schemas/test-recommendations-v1.schema.json).

`vee tests plan --base main --profile impacted_rust --output json` previews trusted Go/Rust impact-targeted verification profiles without launching them. The output contains the exact executable and argument arrays that the verifier would use, target list, source snapshot ID, digest of the selected verification profile, impact limitations, and `execution_performed: false`. It refuses incomplete impact analysis and plans above 128 targets. JSON follows [impacted-test-plan-v1.schema.json](schemas/impacted-test-plan-v1.schema.json). Use `vee verify --profile <id> --impacted-tests` to explicitly execute an applicable configured profile.

Use `vee verification diagnose RUN_ID --output json` or MCP `diagnose_verification` to inspect a saved failed/timed-out verification. Vee verifies content-addressed log artifacts and the exact snapshot manifest, then extracts bounded compiler/test failure lines from common Go, Rust, TypeScript, Python, and generic output, including structured `go test -json` events, JUnit XML failure/error records, nextest flaky-attempt and retry-failure records, and nextest libtest JSON `failed`/`timeout` test events. Nextest's JSON format is experimental and may change; JUnit reports are preferred for stable machine-readable runs. XML DTD/entity declarations are rejected. Vee links only changed paths named directly in a diagnostic record. Pattern matches are deterministic evidence pointers, not root-cause conclusions; unavailable/tampered output or unrecognized formats are reported as limitations. JSON follows [verification-diagnosis-v2.schema.json](schemas/verification-diagnosis-v2.schema.json); v1 remains available for historical output.

`vee acceptance report --review REVIEW_ID --output json` and MCP `acceptance_traceability` extract Markdown checkbox/list criteria or structured criteria from a review's saved work item and show stable Vee criterion IDs, original source IDs when supplied, candidate changed paths, language impact links to likely test references, and verification runs bound to that review snapshot. Structured criteria use a JSON/YAML document with `schema_version: 1` and `requirements: [{ id, text }]`, defined by [acceptance-criteria-v1.schema.json](schemas/acceptance-criteria-v1.schema.json); source IDs are retained for traceability. Impact edges include analyzer certainty and source lines, and are emitted only for the exact review snapshot; MCP also rejects a stale source snapshot. They are candidate links, not coverage evidence; every criterion remains `needs_human_review`. Analyzer limitations are included in the report. JSON follows [acceptance-traceability-v1.schema.json](schemas/acceptance-traceability-v1.schema.json).

`vee acceptance validate --review REVIEW_ID --mapping acceptance.json --output json` checks a human-authored mapping against the exact review, snapshot, and work-item digest. It rejects unknown criteria, paths outside the snapshot, verification runs from another snapshot, duplicate assessments, non-passing runs attached to a `met` assessment, and stale mappings. Configure `policy.acceptance.require_passing_verification: true` to require at least one passed verification run for each `met` criterion, and `policy.acceptance.required_verification_profiles: [unit, integration]` to require named passed profiles for every such criterion. The effective policy is included by digest; protected `.vee/policy.yaml` settings can strengthen repository settings and cannot be weakened by them. Human `met` assessments remain attestations; they are not proof of behavior. Add `--gate` to return `0` when the acceptance policy passes, `1` for a criterion assessed not met, and `2` when assessments or required evidence are incomplete. This command does not change or replace `vee gate`. Mapping and result formats are defined by [acceptance-mapping-v1.schema.json](schemas/acceptance-mapping-v1.schema.json) and [acceptance-validation-v1.schema.json](schemas/acceptance-validation-v1.schema.json).

The CLI and MCP review, verification, impact, and gate paths call the same `vee-application` services. Task cancellation is cooperative: Vee terminates the active provider child process; snapshot capture and local database operations complete or fail at their next synchronous boundary.

Findings merged across configured reviewers retain sorted `reviewer_ids` to expose independent reviewer agreement in reports and persisted records. When multiple reviewers report the same fingerprint, `reviewer_arbitration` preserves each report, marks severity/confidence/rationale disagreement, lists matching global or reviewer-specific rules, and records whether the final gate blocks it. Markdown reviews include the same arbitration summary.
