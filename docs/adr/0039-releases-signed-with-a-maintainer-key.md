# ADR 0039: Releases signed with a maintainer key

- **Status:** Accepted
- **Date:** 2026-11-27

## Context

Each release archive has a checksum and a GitHub build provenance
attestation. Both come from the release workflow. Whoever can change that
workflow, or compromises GitHub Actions for the repository, can publish
archives that pass both checks. A signature from a key the maintainers hold
outside CI says that a maintainer checked the release and vouches for it.

## Decision

**SSH signatures over `sha256.sum`.** A release's `sha256.sum` lists the
digest of every archive, so one signature covers every binary.

- `ssh-keygen -Y sign` signs it with the namespace `vee-release`, which
  keeps the signature from being valid as any other kind of SSH signature.
- The signature is uploaded to the release as `sha256.sum.sig`.
- SSH keys were chosen over minisign, GPG or cosign key pairs:
  - maintainers already have SSH keys, often hardware-backed
    (`ed25519-sk`);
  - verifiers already have `ssh-keygen`, through OpenSSH 8.0 or later, so
    they need no new tool.

**Signing happens on the maintainer's machine, never in CI.** A key stored
as a CI secret would fall to the same compromise that provenance already
covers. `scripts/release-signature.py sign`:

1. downloads the published `sha256.sum` and every archive it lists;
2. checks each archive's digest and its provenance attestation;
3. signs, then checks the signature against `.github/release-signers`,
   so a key that is not listed cannot produce a published signature;
4. uploads the signature.

**Trusted keys live in the repository.** `.github/release-signers`, in the
allowed-signers format, lists the keys for the principal `vee-release`. Like
any other change, adding or removing a key is a reviewed commit.

**Verification.** `scripts/release-signature.py verify --tag vX.Y.Z
<archive>` checks the signature against that file, then each archive's
digest. `--directory` works on files already downloaded, without `gh`.

## Consequences

- A release is signed only once a maintainer runs the script. The
  roadmap keeps "the first signed release" open until a key is listed and
  used.
- **The installers do not check the signature.** They are generated by
  `dist` and check checksums only; signature checking is a separate step.
- **Removing a key unsigns releases.** Releases signed with a removed key
  no longer verify against the current file, so a maintainer re-signs
  them.
- **CI tests the whole path:** a throwaway key signs a disposable release,
  and the test checks that verification refuses:
  - an unsigned release;
  - a key that is not listed;
  - a tampered archive;
  - a tampered checksum file;
  - an empty signers file;
  - a file name that escapes the release directory.
