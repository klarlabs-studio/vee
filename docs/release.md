# Release qualification

Vee installs from release binaries, a container image, or a source checkout. A crates.io release is not configured: internal workspace crates use path dependencies.

## Before tagging a version

1. Confirm the intended workspace version and update `Cargo.lock` with the workspace manifests.
2. Regenerate the UI bundle with `cd web && npm ci && npm run build`; commit `web/dist` with its source changes.
3. Run `python3 scripts/verify-clean-build.py` from the repository root with Rust stable, Git, Node.js/npm, and the Playwright Chromium browser available. It stages the current source tree in a temporary directory without `.git`, `.vee`, `target`, or `node_modules`, runs `npm ci`, rebuilds and verifies generated UI assets, runs all browser workflows, checks formatting and strict workspace Clippy, runs the locked Rust workspace tests and build, installs the CLI into a temporary prefix, and checks the installed executable.
4. Run `python3 scripts/benchmark-review.py --vee target/debug/vee --output docs/performance-baseline-YYYY-MM-DD.json`. Keep the recorded OS, Rust, Python, Vee version, and binary digest with the measurements. Compare only with a baseline from equivalent hardware and tool versions.
5. Inspect the acceptance output and `git diff --check`; confirm the web job and every Linux/macOS/Windows Rust CI job passed for the exact candidate revision. The clean-source script runs formatting and strict Clippy locally, but local checks do not replace the hosted matrix.
6. Review installation and upgrade instructions in `README.md`, then tag the exact tested commit.

## Supported installation and upgrade

Install a release with the shell or PowerShell installer attached to it, or use the container image (see the README). To build from source instead, you need Rust stable and Git: install the CLI from a checkout with `cargo install --path crates/vee-cli --locked`. Upgrade by checking out the desired revision and rerunning the command with `--force`. Repository review history is stored under `.vee/`; recommend a backup before upgrades that include storage migrations.

Provider CLIs and credentials are configured by each user and are not bundled. Node.js is needed to rebuild the checked-in local UI bundle and to run its browser workflow tests, not to build a checkout that already contains current `web/dist` assets.

## Publishing a release

Releases are built by [dist](https://github.com/axodotdev/cargo-dist), configured in `dist-workspace.toml`. `.github/workflows/release.yml` is generated by `dist generate`; after regenerating it, run `python3 scripts/patch-release-workflow.py`, which fixes the container job that dist 0.34 renders with a broken path and without permissions.

Pushing a version tag publishes a release, so tag only a tested commit.

1. **Tag the commit.** Push a `vX.Y.Z` tag that matches the workspace version. A suffix such as `-rc.1` makes it a prerelease. The workflow then:
   - builds `vee` for Linux x86_64 and arm64, macOS arm64 and x86_64, and Windows x86_64, each on a native runner;
   - writes a checksum for each archive and a combined `sha256.sum`;
   - attests build provenance;
   - creates shell and PowerShell installers;
   - publishes the GitHub release.
2. **Container image.** After the release is announced, `.github/workflows/container.yml`:
   - downloads the release's Linux binaries and checks them against their checksums and attestations;
   - packages them with the `release` stage of `Dockerfile`;
   - pushes `ghcr.io/klarlabs-studio/vee:<tag>` and attests the image.

   A prerelease does not move `:latest`.
3. **Check the release.** Download an archive and run `gh attestation verify <archive> --repo klarlabs-studio/vee`, then install it with the shell installer.

Pull requests run `dist plan`, which checks the release configuration without building.

The installers check each archive against the checksum built into them. `VEE_DOWNLOAD_URL` points them at a mirror of the release files.

## Release boundary

- **Do not advertise a registry package or an installer for Windows** until it is configured and tested.
- **Releases are not signed with a maintainer key.** Their integrity rests on GitHub's provenance attestations and the published checksums.
- **Hosted acceptance is still open.** Hosted CI runs on Linux, macOS and Windows; the GitHub lifecycle acceptance runbook has not yet been run against a real repository.
