# Initial architecture

The workspace uses `vee-core` for domain contracts, pure policy logic, and the repository ports (`vee_core::ports`); `vee-store-sqlite` as the SQLite adapter that implements those ports; `vee-process` as the subprocess adapter for reviewer providers and verification commands; `vee-application` for shared review, verification, impact, and gate use cases, which depend only on the ports; `vee-git` as the Git snapshot adapter; and `vee` for CLI and MCP transports, which open the SQLite store and pass it to the application services. CLI and MCP both use the shared application services, while current-snapshot capture is also shared. Impact analysis parses Rust syntax for references, uses `gopls` semantic references for Go, and uses the TypeScript language service (`tsserver`) for TypeScript/JavaScript when each tool is available and the live workspace matches the reviewed snapshot. Their fallbacks remain explicitly heuristic. These are bounded, evidence-backed relationships rather than a complete call graph, and results report analyzer status, tool version, uncertainty, and source coverage. TypeScript automatic type acquisition is disabled and project-local plugins are not enabled. No Warden integration is present.

Optional Git hosting integrations implement the provider-neutral `vee-hosting::GitHostingProvider` port. Hosting identities include the server host as well as repository path so self-hosted instances do not collide. PR revisions bind diff reads and publication; review checks and finding threads carry Vee snapshot IDs and idempotency keys. The GitHub REST/GraphQL adapter reads PR metadata/files, upserts check runs by `external_id`, posts or edits inline finding comments owned by its configured actor, resolves/reopens mapped review threads, and verifies `X-Hub-Signature-256`. Review-comment scans, check-run scans, and GraphQL review-thread reconciliation each fail closed at a 3,000-item/page bound. The GitLab REST adapter reads MR metadata and revision-bound diffs, publishes deterministic commit statuses, synchronizes fingerprinted MR discussions, and verifies signed webhook envelopes with a timestamp window. The application service verifies an incoming webhook before creating an atomic SQLite lease; retries are suppressed after completion, while expired or explicitly released claims can be retried after failure. Leases are renewed while event handlers run. `vee-http` exposes an optional `router_with_webhooks` and `serve_with_webhooks` transport; handlers receive only adapter-verified envelopes and run on blocking workers under a durable lease. The listener checks the configured repository, current open PR base/head, and exact locally available commit range before review; it publishes a snapshot-bound check and inline comments only on added diff lines, and does not fetch event-supplied commits. Credentials are sourced from environment variables and never serialized into repository config. GitLab webhook verification fetches the live MR base and pairs it with the signed event head; the shared handler re-fetches and compares the current revision before reviewing. Remaining work includes broader provider adapters, repository-level provider configuration, retention cleanup, and real provider app installation testing. See [GitHub's Checks API requirements](https://docs.github.com/en/rest/checks/runs), [pull request review comment API](https://docs.github.com/en/rest/pulls/comments), [GitLab signing tokens](https://docs.gitlab.com/user/project/integrations/webhooks/#signing-tokens), and [GitLab merge request webhook events](https://docs.gitlab.com/user/project/integrations/webhook_events/#merge-request-events).

Azure DevOps implements the same hosting provider port for webhook-driven reviews. Its Service Hook adapter verifies the configured Basic-auth password (configure the hook to use HTTPS), normalizes PR creation and active source updates into review events, maps collection-style repository URLs through the payload's project metadata, and allows the shared handler to re-fetch the live PR and compare exact base/head commits before review. Azure events enter the same durable delivery lease and retry flow as GitHub and GitLab. PR close and non-code update notifications are acknowledged without starting a new review.

Bitbucket Cloud webhook events verify the provider's HMAC-SHA256 request signature. Bitbucket Data Center webhook events (`pr:opened`, `pr:from_ref_updated`, `pr:modified`) verify `X-Hub-Signature: sha256=...` the same way at `/api/webhooks/bitbucket-data-center` ([ADR 0047](adr/0047-bitbucket-data-center.md)). Gerrit event ingestion accepts signed `patchset-created`, `change-restored`, `change-abandoned`, and `change-merged` payloads, verifies a relay-provided `X-Gerrit-Signature: sha256=...`, and uses the event patch-set SHA only as a freshness check; Vee fetches the current Gerrit change and derives the base commit before capturing the local range. Gerrit's official webhook plugin documents HTTP event delivery but does not document a payload signature header, so deployments must put an HMAC-signing relay or trusted signing reverse proxy in front of Vee. The ingress is available at `/api/webhooks/gerrit`; the HMAC secret is read from `VEE_GERRIT_WEBHOOK_SECRET` by default. Unsigned payloads are rejected.

GitHub, Bitbucket, Azure DevOps, and Gerrit pull request comments and GitLab merge request notes can also be retrieved through the read-only `PullRequestReviewIssuesProvider` port. Adapters check the pull request revision before and after bounded comment retrieval; if it changes, retrieval fails as stale. Gerrit resolves the current patch-set SHA first and requests comments only for that revision. Returned provider comments are explicitly marked untrusted and gate-ineligible so an agent can investigate them without treating someone else's review text as Vee evidence. GitLab system notes, deleted Bitbucket comments, and Azure DevOps system/deleted comments are excluded. Gerrit also publishes revision-bound tagged gate summaries and fingerprinted inline threads through the standard review endpoint; it checks the current revision before and after publishing, updates only Vee-owned threads, and reconciles resolution from the latest thread comment. Gerrit credentials support bearer auth or HTTP Basic auth for username plus HTTP password. Gerrit's standard review API has no universal check-run surface, so the summary is a change message; Checks UI integration depends on a separately installed plugin.

The first invariant is fail-closed behavior: an unavailable reviewer produces `incomplete`, never `pass`. Gate checks bind to current source and effective config digests and persist an immutable decision. Snapshot IDs hash a canonical manifest of changed file metadata and contents; `.vee.yaml` is fingerprinted with effective config, outside the source manifest. Git capture is implemented in `vee-git` and is invoked through `vee-application` by both transports.

SQLite schema evolution uses `PRAGMA user_version` and ordered, transactional migrations. Schema version 1 creates the initial review and evidence tables; version 2 adds finding-scoped verification records and their lookup index; version 3 adds an explicit effective-config digest to persisted gate decisions and backfills it from each review; version 4 adds content-addressed artifact records and verification stream references; version 5 adds the provider response cache; version 6 adds immutable snapshot manifests and indexed evidence records; version 7 adds leased webhook delivery replay protection. The v6 migration recovers valid snapshot manifests from persisted review payloads and retains a legacy placeholder only when a prior payload cannot supply a digest-valid manifest. Evidence records are normalized from the prior evidence table. Newer database versions are rejected without attempting a downgrade.

Every gate decision carries both the effective configuration digest and policy digest. The decision identity includes each digest independently, and CLI, MCP, and history outputs expose the configuration digest so consumers can audit exactly which configuration was evaluated.

Gate evaluation also binds the source evidence used to assess blocking findings. A finding can block only when its cited source evidence is classified as observed on the exact changed line in the captured snapshot. Missing locations or unobserved lines yield an incomplete decision. Evidence and its digest are retained in replay inputs so CLI and MCP gate re-evaluation applies the same rule locally.

Verification captures bounded stdout and stderr, redacts configured environment values, and persists the resulting bytes as content-addressed files. The command digest binds the configured profile, executable identity and content digest, and digests of present allowlisted environment values without retaining raw values. The executable and allowlisted environment are checked again after execution; a change makes the run incomplete and it is not persisted as verification evidence. Completed verification runs, including failed checks, and their artifact references are committed in one SQLite transaction. A stale run is rejected before its artifacts are registered as evidence. Transitive tools, operating-system state, and external services are outside this fingerprint.

Provider response reuse is keyed by the complete serialized reviewer request, provider kind, model, arguments, limits, provider version, executable content digest, and a digest of allowlisted environment values. Only providers with a known version and readable executable are cacheable; failed or schema-invalid responses are never stored. Environment values are represented only by digests in cache and configuration identity. Reviewer outcomes identify reused results as `cached`, and policy treats them as completed analyses.

After analysis and source-evidence attachment, the review service recaptures the configured Git scope before evaluating the gate. If a mutable scope changed while reviewers ran, or Vee cannot revalidate it, the run is incomplete and records a snapshot-consistency outcome. Commit scopes remain bound to their immutable commit tree; staged scopes intentionally exclude unstaged worktree edits.

Application verification checks the same recorded change scope immediately before and after running a configured command. If source differs before execution or changes while it runs, Vee rejects the result and does not persist verification evidence for the stale snapshot. For staged snapshots, the command runs against the checkout, so verification additionally requires tracked files to match the index and no non-ignored untracked files; this prevents staged evidence from accidentally describing unstaged bytes.

Configuration is loaded by the application boundary. The domain config loader merges versioned user provider defaults with repository config before validating reviewer references; repository provider entries win on ID collision. CLI and MCP share this loader, and the resolved configuration (including user provider settings and repository instructions) is fingerprinted for stale-gate checks. User config contains provider metadata only; credentials are resolved from the process environment by the provider adapter.

Named policy profiles are resolved in the domain config before protected local policy is applied. A review persists the selected profile ID; gate rechecks load the current profile with the same ID, reapply protected policy, and compare the resulting effective configuration digest before reevaluation.

Waivers are separate SQLite records keyed to a finding fingerprint and exact snapshot. The pure gate evaluator applies only schema-v1 records active at evaluation time and matching a finding in that snapshot. Applied waiver IDs contribute to the evidence digest; expiry or snapshot changes restore the finding's normal policy behavior. The CLI records local provenance and caller-supplied author attribution.

Finding fingerprints are computed from normalized category, repository-relative path, and a source anchor read from the exact captured change snapshot at the finding location. This keeps identity stable across line shifts and reviewer paraphrases while distinguishing changed code. If no source anchor can be resolved, normalized rationale is the fallback; that case is less robust across wording changes.

Reviewer execution crosses the `vee-application::ReviewProvider` port. The current `CliReviewProvider` adapter delegates to the bounded subprocess implementation in `vee-process`, which also runs trusted verification commands; the application service remains responsible for finding normalization, provenance, evidence attachment, persistence, and deterministic policy evaluation. Provider-adapter tests inject a test implementation at this port so application behavior can be checked without invoking a real model or executable.

Generic provider subprocesses receive review context over stdin and run from an empty disposable working directory. This prevents ordinary relative file reads/writes from touching repository content while keeping configured relative executable paths resolvable against the repository at launch. It is defense in depth only; providers run with the user's OS identity and can still access absolute paths or network resources permitted by the host.

Enabled reviewers are prepared in configuration order and executed through a bounded worker pool (`review.max_concurrency`, default 4, valid range 1–32). Results are placed back into reviewer slots before normalization and persistence, so provider completion timing does not change report ordering or policy inputs. Adapter panics become explicit reviewer execution failures and therefore cannot accidentally yield a passing gate.

Provider context contains both baseline bytes from the snapshot's recorded base OID and current bytes verified against the changed-file manifest. Added paths have no baseline; deleted paths retain baseline content. Baseline plus current content count toward the per-file and per-review context limits. Binary/non-UTF-8 data and Git LFS pointers are identified in context and make that reviewer outcome incomplete because the underlying change was not fully inspectable. Git LFS objects are never fetched implicitly.
